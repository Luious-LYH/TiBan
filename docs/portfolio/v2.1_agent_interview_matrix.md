# v2.1 Agent 应用岗：JD、面试追问与项目证据矩阵

> 调研日期：2026-08-20。目标岗位是中国中大厂的大模型应用 / Agent 研发与算法岗位。本文只把仓库中能定位到代码、测试或 Artifact 的能力标为“已实现”；框架名、计划项和界面文案不算实现证据。

## 1. 结论先行

2025–2026 年的招聘信号已经从“调用大模型 API、会用 LangChain”转向八类可追问能力：

1. 能否把业务任务拆成可执行、可验证的 Planning / Workflow；
2. Tool Calling 是否有类型约束、权限边界、失败收据与恢复策略；
3. Memory 是否区分短期状态与长期画像，写入是否有依据、隔离和生命周期；
4. RAG 是否真的做了召回、排序、引用和 Recall@K，而非把静态文本塞进 Prompt；
5. 是否会做 Context Engineering，包括上下文选择、预算、压缩与污染防护；
6. 是否有任务级 Eval、Golden Set、失败归因和回归门禁；
7. Provider / Tool 异常时是否可降级、重试、回滚并保持幂等；
8. 是否量化端到端延迟、Token、成本和每一步可观测性。

对本项目的判断是：**评测、结构化工具收据、可观测执行轨迹、演示级稀疏检索、一次受控恢复、上下文预算和 Session 重放已经形成真实证据；Planning 与 Memory 仍是受控演示实现，Provider 真实 Token/成本账本仍是缺口。**

本轮最有面试收益的最小增强不是接入更多框架。以下状态已在 v2.1 落地：

- P0 已完成：工具失败注入、统一错误码、最多一次受控重试和 Recovery trace；
- P0 已完成：病例证据直取升级为轻量可解释稀疏检索，并新增 Recall@1/3；
- P1 已完成：Context Manifest 与预算统计，明确每次运行“选了什么、丢了什么、为什么”；
- P1 部分完成：规则路径 usage ledger 明确 `model_calls=0`、真实 usage/cost 为 `null`；Provider usage 解析仍待完成；
- P1 已完成：有界进程内 Checkpoint/Replay 与真实 NDJSON 阶段事件流，不写 seed。

实现与验证入口：`backend/app/services/portfolio_agent_runtime.py`、`portfolio_eval_service.py`、`backend/tests/test_portfolio_agent.py`、`artifacts/eval/latest.json`。

## 4. 推荐的 v2.1 实现顺序

### P0-A：可恢复 Tool Runtime

这是最能同时覆盖 Planning、Tool Calling、Eval 和容错的增强。

最小验收：

- Tool 有独立输入/输出 Schema 和统一错误码；
- 可在测试中确定性注入一次 `timeout` 或 `unavailable`；
- Runtime 记录第一次失败、是否 retry、replan 原因和最终状态；
- 限制最大尝试次数，避免循环；
- Eval 分别报告工具首次成功率、恢复成功率、最终任务完成率；
- 不产生真实外部副作用。

面试表达：

> 将工具层从“函数能调用”升级为类型化、可观测、可恢复的执行单元；通过故障注入验证超时重试和受控降级，并用恢复成功率而非 Happy Path 截图衡量鲁棒性。

### P0-B：轻量 Evidence Retrieval

当前语料只有 19 条事实，优先实现可解释的稀疏检索，比引入复杂向量基础设施更合理。

最小验收：

- Evidence corpus 与 Case 解耦；
- Query 经元数据过滤后做关键词/BM25 排序；
- Receipt 返回 rank、score、evidence_id 和 source；
- 评测 Recall@1、Recall@3、引用覆盖率；
- 无召回时显式返回 `insufficient_evidence`，不能静默使用答案字段。

面试表达：

> 针对小规模垂直知识库选择可解释稀疏检索，结合部位和任务元数据过滤；用 Recall@K 与证据引用覆盖率验证检索，而不是把静态病例事实包装成 RAG。

### P1-C：Context Manifest + Token/成本账本

最小验收：

- 每个上下文块记录来源、优先级、可信级别、估算 Token 和取舍原因；
- 设置总预算并产生 `included/dropped` 清单；
- Provider usage 存在时记录真实 Token，不存在时标记 unavailable；
- Trace 汇总模型调用次数、Provider latency 和规则工具 latency；
- 不在代码、日志或文档中保存 Key、内部地址和自由文本隐私数据。

## 5. 面试时可讲的八段结构

每段按“业务问题 → 设计决策 → 证据 → 边界”回答，避免只背概念。

1. **为什么不是普通 Chat？** 医生研修需要完成事实评分、证据核验和画像更新，因此使用显式执行图；代码证据是五节点 trace。
2. **为什么不是开放 ReAct？** 医疗教学 Demo 的工具集合小且边界明确，采用受控计划更可预测；当前不声称模型自主规划，v2.1 用故障触发的有限 replan 展示动态性。
3. **Tool Calling 如何可信？** 工具名、入参、出参、证据 ID、耗时和错误都进入 receipt；下一步补独立 Schema 与故障注入。
4. **Memory 为什么不会乱写？** Eval 只生成带理由的 Delta preview；正式持久化与评测隔离。当前 JSON seed 是 demo 局限，计划迁移 runtime event store。
5. **RAG 做了吗？** 当前只有 evidence lookup，不称为 RAG；完成 BM25 + Recall@K 后再写进简历。这种诚实区分本身能体现工程判断。
6. **如何评测？** 任务完成、工具正确、证据覆盖、安全、结构化和延迟分维度统计；100% 是固定规则回归，不代表模型临床能力。
7. **异常如何处理？** Provider 已有 timeout、主备 attempts 和规则降级；v2.1 用 Tool failure injection 补足 Agent 层恢复证据。
8. **性能数字怎么解释？** 当前 P50/P95 只测本地规则 Runtime；模型、网络和前端不在口径内。后续将 HTTP E2E、Provider latency、Token 和成本拆开报告。

## 6. 当前禁止写入简历的表述

- “基于 LangGraph/ReAct 实现自主规划”：当前是自研确定性五节点工作流。
- “构建向量数据库与混合 RAG”：当前仅按病例 ID 直取证据。
- “长期记忆召回准确率提升 XX%”：当前没有记忆检索 Golden Set。
- “工具失败恢复率 XX%”：尚未完成 Tool fault injection。
- “VLM P95 低至 1 ms”：当前毫秒级数字是本地规则服务耗时。
- “Token 成本降低 XX%”：Provider 尚未形成 usage/cost Artifact。
- “支持多 Agent 协作或 MCP”：仓库没有相应的运行证据，且不是本轮必要项。

## 7. 完成增强后的优先简历句式

以下句式必须在对应增强和 Artifact 完成后才能使用：

> 面向消化内镜研修场景设计可观测 Agent Runtime，将作答处理拆为 Plan、Tool Act、Evidence Observe、Verify 与 Memory 五阶段；以类型化 Tool receipt 记录参数、证据、耗时和错误，并通过故障注入验证受控重试与降级恢复。

> 针对小规模垂直证据库实现元数据过滤 + 可解释稀疏检索，构建 query-evidence Golden Set，以 Recall@K、引用覆盖率和不足证据拒答率评估 Grounding，避免将静态 Prompt 拼接包装为 RAG。

> 建立病例级 Agent 回归集，分开统计任务完成、工具选择、证据覆盖、安全、结构化、恢复成功与 P50/P95；所有数字绑定 JSON/Markdown Artifact，并明确规则 Runtime、模型调用和端到端延迟的测试口径。
