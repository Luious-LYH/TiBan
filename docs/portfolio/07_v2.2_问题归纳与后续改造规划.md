# v2.2 问题归纳、参考调研与后续改造规划

> 状态：规划文档。本文只归纳问题和锁定后续改造方向，不在本轮修改代码。
>
> 目标产品：**内镜医师刷题 Agent**，即“真实题库业务 + Agent 陪练/讲题/错题复习 + 可复现模型评测”。
>
> 适用对象：研三求职作品集、面试展示和后续迭代。不是临床诊断系统，也不把公开 benchmark 包装成临床题库。

## 0. 先给结论

当前 v2.1 的根问题不是颜色、间距或某一个按钮，而是产品主线偏了：

1. **产品身份偏成了“病例报告描述 Demo”**，而用户真正要展示的是“内镜医师刷题软件”。
2. **题库以病例卡片为单位，而不是以题目/知识点为单位**；用户看见 5 个病例，自然会认为只有 5 道题。
3. **后端存在练习 API 和 50 条派生变体，但没有成为前端主流程**；派生题也不是医生编审的正式题目。
4. **Agent 目前更像固定的规则运行器**：能记录步骤和收据，但没有围绕“选题—提示—讲题—评分—复习—记忆”完成用户价值闭环。
5. **开放题评分没有真正的题库知识库 RAG 链路**；当前小语料稀疏匹配不能回答“为什么这样评分、依据来自哪里、如何避免答非所问”。
6. **评测能力没有成为用户可操作的产品**；有自定义模型 API 的后端入口，但当前主导航和评测页没有让用户选择评测集、输入一次性授权、真实调用并查看逐题结果。
7. **内部工程术语泄漏到用户界面**，如 Run、Receipt、Memory、Context budget、Precision/Recall；这些可以留在“查看运行详情”里，不能作为刷题主界面语言。
8. **题库没有稳定的获得、导入和自动生成路径**；即使把 5 个样例扩成 50 个派生问题，也不等于用户可以持续建立自己的题库。
9. **Tutor 出现得太晚**；用户在思考、看不懂选项或需要提示时无法立即追问，Agent 没有进入刷题过程本身。
10. **多 Agent 只有概念、没有职责边界**；Generator、Judge、Tutor、Mentor、Repair、Evaluation 应有不同提示词、工具、上下文和记忆范围，普通解析/索引 ETL 则不应冒充 Agent。
11. **运行时缺少明确取舍**；不能一边声称自研 Agent，一边把路由、状态、重试全部交给框架且无法解释。
12. **数据模型写死在内镜业务**；未来扩展到其他医学学科或通用题库时，不应该重写练习、复习、RAG 和评测引擎。

后续所有改造都围绕一个成功时刻：

> 研修医选择一个部位和知识点 → 完成单选/多选/判断/问答 → Agent 根据题目和知识库给出逐项讲解 → 更新掌握度和下次复习时间 → 推荐下一道真正相关的题。

## 1. 当前 v2.1 的事实盘点

| 维度 | 当前事实 | 用户感知 | v2.2 目标 |
|---|---|---|---|
| 题库展示 | `portfolio_cases.json` 有 5 个病例；`real_sample_knowledge.json` 有 10 张公开样例图 | 只有 5 个“病例”，不像题库 | 按题库/部位/知识点展示题量，病例只是题目素材的一种载体 |
| 练习变体 | 后端 `/api/practice/questions` 可由 10 张图派生约 50 条变体 | 入口没有题型筛选，能力像不存在 | 以正式 `question_id` 为核心，支持题型、难度、知识点、错题和收藏筛选 |
| 题型 | 后端已有单选、多选、判断、问答评分、报告修改字段，但前端主入口不承载它们 | 用户只能写一段自由文本 | 单选、多选、判断为主；问答、配对、填空、图像定位作为扩展 |
| 内容来源 | 题目由 benchmark QA 和规则模板派生 | 看起来像测模型，不像医生培训题 | benchmark 与教学题库分离；教学题由知识点、教学目标、干扰项和参考资料组成 |
| Agent | 固定 `retrieve_case_evidence → fact_rubric_grader → safety_guard` | 有运行日志，但没有明显的“陪练老师”价值 | Agent 按学习意图选择提示、讲题、评分、复习和记忆工具 |
| 评分 | 小语料 BM25-equivalent + 关键词事实命中 | 开放题可能只是在匹配词 | 客观题确定性评分；主观题采用 Rubric + 知识库证据 + LLM judge 二次评分 |
| RAG | 没有题库知识库的向量索引、分块、混合召回和重排 | 不能解释知识依据 | 题目/讲义/参考资料分库，dense+sparse+rerank，返回可读证据片段 |
| 记忆 | 有运行态画像和少量复习字段 | 看不出长期带教 | 分离会话记忆、作答事件、学习画像、长期知识点记忆和复习卡状态 |
| 模型评测 | 后端有 `/api/models/custom-evaluate`，当前主 UI 没有完整入口 | 用户不能选择 API、评测集并确认真实调用 | BYOK 一次性调用，隐藏答案，逐题记录响应、评分、延迟和失败原因 |
| 用户语言 | 页面中出现 Agent Runtime、Receipt、Memory、Context budget 等开发词 | 像工程验收台，不像刷题软件 | 主界面只说“提示、讲解、复习、掌握度”；高级运行信息折叠展示 |
| 图像 | 图片来源真实，但题卡图像尺寸和信息层级不够统一 | 视觉上像样例列表 | 统一比例、contain、放大、缩略图、加载/失败/无图状态 |
| 工程结构 | `api.ts` 与 `v3Api.ts` 有重复能力；旧页面代码存在但不在主路由 | 维护和接手困难 | 一个 API client、一个题库模型、一个评测模型、一个版本化数据源 |

## 2. Scope Lock：先锁产品范围

### 2.1 产品承诺

**为消化内镜研修医提供可持续刷题和错题复习。Agent 负责理解学习意图、给提示、逐项讲解、对开放回答按题目 Rubric 评分、更新知识点掌握度并安排复习；模型评测是独立的研究入口。**

### 2.2 用户角色

- **研修医**：选题、作答、看讲解、复习错题、查看知识点薄弱项。
- **题库维护者/带教老师**：导入题目、维护参考资料、查看 AI 生成/Judge 结果、管理题库版本。
- **个人题库创建者**：上传自己的 PDF/Word/Markdown/CSV/Anki 导出内容，选择生成范围并在使用中反馈错题。
- **模型评测者/面试官**：选择冻结评测集，输入自己的 OpenAI-compatible API，查看逐题结果和指标。

### 2.3 必须保留、删除、延后

**必须保留（MVP）**

- 食管、胃、小肠三个题库入口；预留结直肠、胶囊内镜、基础操作等大类。
- 单选、多选、判断、简答四种题型；至少展示题型筛选和题量。
- 纯文本知识题与图文/多模态题并列支持；图片不是题库的必填项，也不是所有内镜知识考察都必须走 VLM。
- 今日练习、顺序练习、错题本、收藏、到期复习、练习记录。
- Agent 提示、逐选项讲解、开放题评分、复习计划和知识点掌握度。
- 刷题过程中可随时展开 Tutor Chat，请求分级提示、追问选项、圈选图像区域或苏格拉底式引导。
- 题库导入/导出和题目校验；至少支持 JSONL/CSV/Markdown 模板，并能从用户文档自动生成多题型草稿。
- Generator → Judge/Critic → Dedup → Publish → Feedback/Repair 的自动题库流水线。
- Tutor、Mentor、Generator、Judge/Repair、Evaluation 五类职责；前台只暴露 Tutor/Mentor 两个自然角色。
- 独立的模型评测页：选择评测集、一次性输入 API、真实调用、逐题结果、汇总指标。

**从主流程删除或折叠**

- 把“器械异常分布、阴性发现计数、报告纠错”当成一级题库分类。
- 在用户主界面直接显示 `Plan/Act/Recovery/Observe/Verify/Memory`、Tool Receipt、token budget。
- 把 `Golden Case`、`Agent Run` 当成研修医必须理解的概念。
- 把所有开发验收、审计和模型 artifact 堆在研修首页。

**延后到增强版**

- 多人协作、排行榜、社交讨论、真实医院账号体系。
- 让所有步骤都由 LLM 自由协商的“群聊式多 Agent”；MVP 使用代码编排的职责型 Agent，只有确需生成、判断或决策的节点调用模型。
- 真实临床报告发布、患者端分享、自动诊疗建议。
- 复杂知识图谱和全量医学文献爬取。

### 2.4 主演示链路

```mermaid
flowchart LR
    A[选择部位/知识点/题型] --> B[开始练习]
    B --> C{客观题或开放题}
    C -->|客观题| D[本地确定性判分]
    C -->|开放题| E[Agent 调用题库检索与 Rubric 评分]
    D --> F[逐项讲解与错因]
    E --> F
    F --> G[记录作答事件与置信度]
    G --> H[更新知识点掌握度和 FSRS 复习卡]
    H --> I[推荐下一题/进入错题复习]
```

## 3. 联网参考调研及可借鉴结论

### 3.1 刷题和记忆产品

- [Anki Getting Started](https://docs.ankiweb.net/getting-started.html)：Anki 把一组字段称为 note，再由 card type/template 生成一张或多张卡；这说明“题目内容”和“展示卡片”应该分离，而不是把所有信息塞进一个文本字段。
- [Anki Card Templates](https://docs.ankiweb.net/templates/intro.html)：模板控制字段在正面/背面如何呈现，可用于同一题生成识别卡、反向卡、填空卡或图像卡。
- [Anki Deck Options / FSRS](https://docs.ankiweb.net/deck-options.html#fsrs)：FSRS 以期望保留率为核心，并根据复习反馈调整间隔；不能只用“答错后固定 1 天”冒充完整记忆算法。
- [Moodle Question Types](https://docs.moodle.org/26/en/Question_types)：成熟题库通常支持单选/多选、判断、匹配、填空、数值、简答、Essay 等多题型，并允许图像或媒体进入题干和选项。
- [Dept. Q. Bank](https://github.com/znu-med/Dept-Q-Bank)：开源医学题库把模块、学科、考试类型、题目导航、标记、错题重做、结果解释和本地进度作为完整业务闭环；题目用 JSON 文件维护，新增模块不需要改代码。
- [ZeroQCM](https://github.com/KNIGHTABDO/zeroqcm)：值得借鉴 QCM/QROC、逐选项 AI 解释、流式讲解、书签和间隔复习；它体现的是“AI 解释服务刷题”，而不是用聊天代替刷题。
- [Stepwise QBank](https://github.com/yagamilight-pk/stepwise-qbank-complete)：值得借鉴 block builder、Timed/Exam/Adaptive 模式、题目 palette、错题/收藏、flashcard、分析页和题目导入管理；其仓库也明确区分演示数据与正式统计。

### 3.2 Agent、工具和可观测性

- [OpenAI practical guide to agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)：Agent 至少要有 model、tools、instructions，并且由模型根据工作流状态选择工具；单轮聊天不能自动称为 Agent。
- [Anthropic Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)：应区分固定 Workflow 与动态 Agent；常见模式包括 routing、parallelization、orchestrator-workers、evaluator-optimizer，并强调工具说明和测试。
- [OpenAI Agents SDK tools](https://openai.github.io/openai-agents-python/tools/)：工具应有清晰 schema，既可以取数据，也可以执行动作；这适合把“提示、评分、更新复习计划”等做成有类型的工具。
- [OpenAI Agents SDK tracing](https://openai.github.io/openai-agents-python/tracing/)：完整 trace 应覆盖模型生成、工具调用、handoff、guardrail 和自定义事件；这些是面试展示证据，应该放在高级详情而不是用户主界面。

### 3.3 RAG、混合检索和评测

- [Qdrant Hybrid Search](https://qdrant.tech/documentation/search/text-search/hybrid-search/)：可以在同一个 collection 中存储 dense vector 和 sparse vector，兼顾语义相似和精确关键词。
- [LlamaIndex Node Parser](https://docs.llamaindex.ai/en/v0.10.18/module_guides/loading/node_parsers/root.html)：分块时继承 metadata，适合把部位、知识点、来源版本和题目 ID 绑定到每个 chunk。
- [LangChain ParentDocumentRetriever](https://reference.langchain.com/python/langchain-classic/retrievers/parent_document_retriever/ParentDocumentRetriever)：小 chunk 负责精准召回，parent document 负责把完整解释带回上下文，适合医学条目和题目讲解。
- [Cohere Rerank](https://docs.cohere.com/docs/rerank)：rerank 用 query 与候选文档的联合相关性排序，适合在 dense+sparse 候选之后减少噪声和 token。
- [Ragas metrics](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)：RAG 不应只看最终答案，至少要看 Context Precision、Context Recall、Faithfulness、Answer Relevancy；Agent 还可看 Tool Call Accuracy、Tool Call F1 和 Goal Accuracy。

### 3.4 内镜数据和评测边界

- [Kvasir-VQA official repository](https://github.com/simula/Kvasir-VQA)：公开数据包含图像—问答标注，适合 VQA/模型实验；它的 QA 是为视觉问答生成和评测服务的，不等于医生课程题库。
- [EndoBench official repository](https://github.com/CUHK-AIM-Group/EndoBench)：面向 MLLM 的内镜 benchmark，覆盖多个场景和任务，并明确要求遵守各原始数据集的 license。它应该进入“模型评测集”，而不是直接作为用户刷题首页。

### 3.5 可获得题库、导入标准与合法使用候选

| 候选来源 | 可直接获得的内容 | 本项目用途 | 使用前动作 |
|---|---|---|---|
| [MedMCQA](https://github.com/medmcqa/medmcqa) | 约 19.4 万道医学考试选择题、主题和解释，仓库标注 MIT | 快速验证医学分类、单选/多选导入、通用医学领域包；不直接冒充内镜专科题 | 固定 commit/版本，保留 citation/license，抽样转换为 Demo 题库 |
| [PubMedQA](https://github.com/pubmedqa/pubmedqa) | 基于 PubMed 摘要的 yes/no/maybe 问答，MIT | 验证“文档证据 → 判断题/简答题 → 引用”的生成链 | 保留 PMID 和原始 split，不把 test answer 用作生成提示 |
| [Kvasir-VQA](https://github.com/simula/Kvasir-VQA) / [Kvasir-VQA-x1](https://github.com/Simula/Kvasir-VQA-x1) | GI 图像—问答、复杂度和解释 | 内镜多模态评测集与少量教学素材来源 | 逐项核对原始图像和派生标注许可；教学题需重新绑定教学目标和解析 |
| [MedQA](https://github.com/jind11/MedQA) | 中英文医学考试选择题 | 评估中文导入、翻译和 taxonomy 映射能力 | 先核验仓库和上游题目许可，只选允许的研究/演示子集 |
| [Open Trivia DB](https://opentdb.com/) / [TriviaQA](https://nlp.cs.washington.edu/triviaqa/) | 通用选择题或带证据开放问答 | 验证“内镜之外”的通用 domain pack，不进入医学页面 | 遵守各自 license/署名要求，与医学库物理隔离 |

这里的原则不是“下载越多越好”，而是先建立 `source_registry`：记录 `source_id / url / version / license / allowed_usage / citation / imported_at / content_hash`。未知许可的数据只能进入本地候选区，不能打包进公开 Demo。

[Moodle Question Bank](https://docs.moodle.org/500/en/question_bank) 证明成熟题库需要分类、子分类、预览、编辑、导入和导出；[1EdTech QTI 3](https://www.1edtech.org/standards/qti/index) 是题目、测试、结果在题库/学习平台/评分系统之间交换的正式标准；[Anki 文本导入](https://docs.ankiweb.net/importing/text-files.html) 则说明 CSV/TSV 的字段映射、deck、note type、tags、GUID 对个人用户更实用。因此本项目采用：**内部 JSONL 真源 + CSV/Markdown 易用入口 + Anki CSV 兼容 + QTI 3 长期互操作**，而不是发明只能自己读取的格式。

### 3.6 自动生成、Judge 与持续评测

- [DeepEval Synthesizer](https://deepeval.com/docs/synthesizer-generate-from-docs) 提供从 txt/docx/pdf/md 文档构造上下文并生成单轮/多轮 golden 的参考实现；本项目借鉴“先构造高质量 context，再生成”的顺序，但题目 schema、教学目标和多题型模板由自己控制。
- [Langfuse LLM-as-a-Judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge) 强调固定 rubric、结构化 score/reason、离线 dataset experiment 和线上 observation 评估；本项目据此把 Judge prompt、模型、阈值和版本全部纳入 artifact。
- [Langfuse evaluation loop](https://langfuse.com/docs/evaluation/core-concepts) 的“线上失败样例回流离线数据集”可直接映射为：用户标记错题 → Repair Queue → 修订 → 回归集 → 新题库版本。

### 3.7 Agent 编排框架与 UI 参考

- [OpenAI Agents SDK orchestration](https://openai.github.io/openai-agents-python/multi_agent/) 区分 manager 调用 agents-as-tools 与 handoff；适合解释“总入口保留对话控制”与“切换到专职 Agent”的差异。
- [LangGraph](https://langchain-ai.github.io/langgraph/index.html) 聚焦 durable execution、streaming、human-in-the-loop 和 persistence；适合题库生成/修订这种可暂停、可恢复的长流程。
- [AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html) 明确建议先优化单 Agent，再在确需协作时使用团队；本项目不采用默认 round-robin 群聊。
- [PydanticAI 多 Agent 指南](https://pydantic.dev/docs/ai/guides/multi-agent-applications/) 把复杂度分为单 Agent、delegation、程序式 handoff、图控制流和 deep agents；可作为 typed agent/tool 的轻量参考。
- [CrewAI](https://docs.crewai.com/index) 强在 role/task/crew 与持久 Flow，但对本项目会引入另一套抽象；不作为第一实现。
- [Semantic Kernel Agent Architecture](https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-architecture) 覆盖 concurrent/sequential/handoff/group-chat 等模式，但主要价值在 .NET/微软技术栈；当前 Python/FastAPI 项目不选。
- [CopilotKit AG-UI](https://docs.copilotkit.ai/ag-ui/introduction) 支持共享状态、工具结果组件、interrupt、子 Agent 和“由 trace/tool event 生成思考步骤，不展示 raw chain-of-thought”；这正是 Tutor Sidecar 的交互原则。
- [Vercel AI Elements](https://elements.ai-sdk.dev/) 提供 streaming message、source、tool、plan、attachment 等组合式 UI 参考；本项目继续使用 React/Vite，可借鉴交互而不必迁移 Next.js。

### 3.8 RAG、记忆与 Provider 基础设施

- [Qdrant Hybrid and Multi-Stage Queries](https://qdrant.tech/documentation/search/hybrid-queries/) 支持 dense/sparse 预取、RRF/DBSF 融合及多阶段查询；[Hybrid Search with Reranking](https://qdrant.tech/documentation/advanced-tutorials/reranking-hybrid-search/) 给出了 wide recall 后 rerank 的标准链路。
- [FSRS 算法说明](https://github.com/open-spaced-repetition/fsrs4anki/wiki/The-Algorithm) 使用 Difficulty、Stability、Retrievability 和 Again/Hard/Good/Easy 评分；项目应接入实现并保留调度对照，而不是自称“类 Anki”后只做固定间隔。
- [LiteLLM](https://docs.litellm.ai/) 可统一 100+ Provider 的 OpenAI 风格输入输出、重试/fallback、预算和成本；但 BYOK 评测必须禁止自动换模型，否则会污染被测模型结果。

**调研结论：**教学题库、Agent 知识库、模型 benchmark 必须是三套不同的数据契约；可以共享公开图像，但不能共享“展示目的、评分方式和用户语义”。平台核心保持领域无关，内镜通过 domain pack 提供 taxonomy、题型模板、grader、Judge rubric、检索模型和 UI 术语。

## 4. 问题清单与对应改造规划

以下每一项都包含：问题 → 为什么重要 → 计划怎么改 → 具体技术流程 → 面试追问和要拿出的证据。

### A. 产品定位和业务闭环

#### A1. 当前主流程不是刷题，而是写病例观察记录

**问题**

当前工作台要求用户输入一段“部位—黏膜—阴性发现—复核边界”的描述。这个任务可以作为开放题，但不应该成为整个产品的默认题型。

**改造规划**

把工作台改成标准练习会话：顶部显示“胃｜病变识别｜单选｜第 3/10 题”，中间是图像和题干，底部是选项/输入框；提交后才打开 Agent 讲解区。

**技术流程/栈**

`session_start → question_selector → question_renderer → submit_answer → grader → tutor_explanation → scheduler → next_question`。

前端 React + TypeScript；后端 FastAPI + Pydantic；会话状态存 PostgreSQL/SQLite；实时讲解用 SSE；复杂 Agent 状态用 LangGraph checkpoint。

**面试追问与证据**

- 追问：为什么不是直接做聊天机器人？
- 证据：同一题可以走“提示、作答、逐项讲解、错题复习”四个明确动作；录制一次完整练习 trace，而不是只展示一段聊天。

#### A2. 病例、题目、知识点混为一个概念

**问题**

一张图被包装成一个病例卡片，再从图像答案派生多个变体；用户无法知道有几道正式题、每道题考什么、同一病例是否有 sibling cards。

**改造规划**

采用三层对象：

- `case`：一组图像/临床教学背景。
- `note`：围绕一个知识点的完整内容和参考资料。
- `question/card`：面向一次练习的具体题干、题型、答案和评分器。

一张病例图像可以承载 5 道不同题，但每道题有独立 ID、掌握度和复习记录。

**技术流程/栈**

数据库表 `cases`、`notes`、`questions`、`cards`、`knowledge_points`；`case_id` 只做素材关联，不作为练习主键。Anki-inspired sibling card 由 note template 生成，复习时可设置 sibling burying，避免连续暴露答案。

**面试追问与证据**

- 追问：为什么要分 note/card？
- 证据：同一 note 可生成“单选识别卡、反向定位卡、图像遮挡卡”；修改解释字段后相关 card 一起更新。

#### A3. 只有三个部位入口，且无法自然扩展

**问题**

食管、胃、小肠作为筛选项是合理的，但现在更像三个按钮，不是可扩展的题库目录。

**改造规划**

使用多级 taxonomy：

```text
消化内镜
├─ 食管：解剖标志、正常黏膜、炎症、息肉/隆起、狭窄、报告规范
├─ 胃：解剖分区、正常黏膜、糜烂/溃疡、息肉、出血、操作器械
├─ 小肠/十二指肠：部位定位、绒毛/黏膜、胶囊内镜观察
├─ 结直肠（预留）：息肉、腺瘤、炎症、分型
├─ 胶囊内镜（预留）：进镜顺序、部位和时间轴
└─ 基础操作（预留）：图像质量、视野、清洁度、器械识别
```

首页显示“已发布题数”和“待复习题数”；没有内容的目录显示“暂未发布”，不伪造题目。

**技术流程/栈**

`taxonomy.yaml` 作为版本化目录；题目用 `body_part_id`、`topic_id`、`knowledge_point_id` 关联。后端返回目录统计，前端不从标题猜部位。

**面试追问与证据**

- 追问：新加“结直肠”是否需要改前端代码？
- 证据：导入一个新 taxonomy 节点和题库 manifest 后，前端自动出现目录和题量。

#### A4. 产品模型写死在内镜，无法扩成医学或通用题库平台

**问题**

如果数据库表、路由、Prompt 和组件都直接使用 `body_part/lesion/endoscopy`，增加心电图、药理学、法律考试或用户自己的语言学习题库时会重复开发整套系统。

**改造规划**

平台核心统一抽象为：

```text
Workspace
└─ Domain
   └─ Collection / Deck
      ├─ Source Document
      ├─ Note / Knowledge Unit
      │  └─ Question / Card
      └─ Practice / Review / Eval artifacts
```

核心平台只负责文档导入、题库生成、练习会话、Tutor Chat、FSRS、RAG、反馈修订和模型评测；每个 `domain_pack` 提供：

```yaml
domain_id: endoscopy
taxonomy: taxonomy.yaml
question_templates: [single_choice, multiple_choice, true_false, short_answer, image_hotspot]
grader_plugins: [objective, rubric_open, image_region]
judge_rubric: rubrics/question_quality_v1.yaml
embedding_profile: multilingual_medical
ui_terms: ui.zh-CN.yaml
safety_policy: education_medical.yaml
```

**技术流程/栈**

后端以 `DomainPackRegistry` 动态注册 taxonomy/template/grader；前端根据 capability schema 渲染筛选器和题型，不读取 `if domain === endoscopy` 的业务分支。首个领域包是 `endoscopy`，第二个用少量通用题验证架构，而不是立刻铺开所有领域。

**面试追问与证据**

- 追问：如何证明不是口头说“可扩展”？
- 证据：导入一个 `general-trivia` domain pack 后，共用同一练习、FSRS、Tutor 和评测 API，只有 taxonomy、模板、grader/rubric 与 UI 术语不同。

### B. 题库内容和题型

#### B1. benchmark QA 被直接当成医生培训题

**问题**

Kvasir-VQA/EndoBench 适合模型 VQA 和 benchmark 评测；“是否有文字、数几个器械、异常在哪个区域”可以作为模型能力任务，但不等于完整的医生知识点教学。当前模板直接围绕这些答案派生题，容易被面试官问“医学教学目标是什么”。

**改造规划**

拆成三类数据集：

1. `teaching_qbank`：面向研修医，题干、知识点、干扰项、讲解和参考资料由 Generator 生成、Judge 自动校验；Demo 阶段 Judge 达标即可发布，人工审核作为可选高质量状态。
2. `agent_knowledge`：用于提示和讲题的教学资料、术语表、常见错误。
3. `model_eval`：冻结 benchmark/holdout，答案隐藏，专供模型 API 评测。

公开图像只记录 `image_source`、license、citation 和使用范围。没有经过“教学目标—题型—解析—Judge”重构的 benchmark 题只标记为“研究评测”，不进入默认刷题计划。

**技术流程/栈**

`source_registry → content_normalizer → generator → judge/dedup → publish_version`；使用 JSON Schema 校验字段，题目状态包括 `draft/auto_approved/published/flagged/deprecated`。发布时生成不可变 `bank_version` 和 manifest hash。

**面试追问与证据**

- 追问：你如何防止把模型 benchmark 包装成医学能力？
- 证据：页面分开显示“教学题库”和“模型评测集”，每个题库有来源、license、生成/Judge 版本和适用范围。

#### B2. 题型过少且用户不能选择

**问题**

用户期待单选、多选、判断等基本刷题形式；当前这些字段在后端存在，但当前主入口未呈现。

**改造规划**

MVP 题型：

- 单选：一个正确选项，支持图像和媒体。
- 多选：多个正确选项，按集合评分，并显示漏选/误选。
- 判断：判断一个医学陈述是否被题干资料支持。
- 简答：输入观察或知识点答案，由 Rubric 评分。

增强题型：配对、填空、数值/计数、图像热点/遮挡、病例时间线。报告改写只能作为“表达训练”子类，不再作为题库主导航。

**技术流程/栈**

`QuestionType` 使用 discriminated union；每种题型有独立 renderer、validator、grader 和 result view。后端不再依靠 `options` 字符串猜题型。

**面试追问与证据**

- 追问：多选怎么处理部分正确？
- 证据：展示 `precision/recall/F1` 或“漏选 1 项、误选 1 项”，并明确最终得分规则，而不是简单判断整串字符串相等。

#### B3. 干扰项质量不足

**问题**

模板式选项很容易出现“最长的就是正确答案”“一眼看出越界选项”“选项之间不在同一个语义层级”等低质量问题。

**改造规划**

每道客观题增加 `distractor_rationale` 和 `misconception_tag`。干扰项来自真实易错点：部位混淆、正常/异常混淆、数量遗漏、观察与诊断混淆、证据不足忽略。导入前跑自动规则和 Judge；抽样人工检查仅用于校准 Judge，不阻塞 Demo 发布。

**技术流程/栈**

`distractor lint` 检查长度偏差、重复词、答案泄露、否定词不一致、选项互斥性；LLM 生成候选后进入结构化 Judge 队列，确定性检查通过且综合分达阈值即可自动发布，用户反馈后可打回修订。

**面试追问与证据**

- 追问：AI 生成题如何保证质量？
- 证据：保留生成 prompt、候选版本、Judge rubric/score、自动重写 diff、用户反馈和最终发布 hash。

#### B4. 把“内镜题库”误解成“所有题都必须带图”

**问题**

内镜研修既包括图像识别，也包括解剖、适应证/流程、器械、分型标准、报告术语、质量控制等纯文本知识考察。若 `media` 被设计成必填，用户上传讲义后只能生造图片题，也无法扩展到其他纯文本学科。

**改造规划**

题型与模态正交：`question_type` 决定如何作答和评分，`modality` 决定输入材料如何呈现和走哪种模型链路。

| modality | 示例 | 渲染/模型路径 |
|---|---|---|
| `text_only` | 纯文本单选、多选、判断、简答、填空 | 文本 renderer；本地 grader 或文本 LLM/RAG |
| `text_with_context` | 阅读一段讲义/病例材料后答题 | 材料区 + 题目区；context-grounded RAG/Judge |
| `image_text` | 内镜图像 + 题干/选项 | 统一图像 viewer；需要时走 VLM |
| `image_hotspot` | 在图上圈选结构/区域 | canvas/overlay renderer；坐标/IoU grader |
| `multi_image` | 两张图比较、序列判断 | gallery/compare renderer；多图 VLM adapter |
| `audio/video` | 后续通用领域预留 | capability 未启用时拒绝导入，不做假支持 |

首页同时提供“知识题”“看图题”“混合练习”筛选；默认学习计划按知识点薄弱度和模态覆盖共同选题，不强迫纯文本题带占位图片。

**技术流程/栈**

`Question` 增加显式 `modality` discriminated union，`media` 对 `text_only/text_with_context` 可为空；`RendererRegistry(question_type, modality)` 选择组件，`GraderRegistry` 选择评分器，`ModelRouter` 只有在输入确有图像且任务需要视觉推理时才选择 VLM。Generator blueprint 同时规划题型、模态和知识点覆盖；纯文本文档默认优先生成 text-only，不自动伪造视觉内容。

**面试追问与证据**

- 追问：题型和模态为什么要拆开？
- 证据：同一 `single_choice` 可分别渲染纯文本和图文题，共用客观题 grader；只有后者的 Tutor 追问触发 VLM，展示成本/延迟路由 trace。
- 追问：如何证明平台可扩展到非医学？
- 证据：导入一份纯文本通用讲义，生成 text-only 多题型并复用同一练习、FSRS、Tutor 和反馈闭环。

### C. 题库创建、导入和扩展

#### C1. 用户无法补充自己的题库

**问题**

当前没有清晰的题库制作规则，用户不知道该准备什么字段，也没有导入错误反馈。

**改造规划**

支持“创建题库”和“导入题库”两条路径：

- 可视化表单：选择部位、知识点、题型，填写题干/选项/答案/讲解/来源。
- 结构化批量导入：JSONL、CSV、Markdown frontmatter、Anki CSV；导入后先进入草稿箱，显示逐行校验结果。
- 文档生成：上传 PDF/DOCX/PPTX/Markdown/TXT，选择领域、难度、题型和数量，由内容工厂生成可刷题库。
- 导出：JSONL/CSV/Anki-compatible CSV；QTI 3 与 `.apkg` 转换作为增强适配器。

**技术流程/栈**

结构化文件走 `upload → schema mapping → validate → draft → publish`；非结构化文档走后文“自动题库工厂”。FastAPI 只接收文件和参数，后台任务完成解析/生成；文件媒体存本地对象目录或 MinIO，元数据入 SQLite/PostgreSQL。

**面试追问与证据**

- 追问：如何做到“加题不改代码”？
- 证据：新增 JSONL 题目后通过校验、发布、刷新题库目录即可出现；保留导入报告。

#### C2. 题库文件没有统一人类可读规范

**问题**

当前内容散落在不同 JSON 和服务内的派生逻辑里，接手者无法判断哪些是原始题、哪些是运行时生成。

**改造规划**

统一目录：

```text
content/
├─ taxonomy.yaml
├─ domain_packs/
│  ├─ endoscopy/
│  └─ general-trivia/
├─ banks/
│  ├─ esophagus-teaching/
│  │  ├─ manifest.yaml
│  │  ├─ questions.jsonl
│  │  ├─ explanations.md
│  │  └─ media/
│  ├─ stomach-teaching/
│  └─ small-intestine-teaching/
├─ knowledge/
│  ├─ anatomy/
│  ├─ lesion-observation/
│  └─ report-language/
└─ eval_sets/
   ├─ endoscopy-mini-v1.yaml
   └─ model-eval-holdout-v1.jsonl
```

运行态作答记录放在 `runtime/` 或数据库，不回写题库 seed。

**技术流程/栈**

Git 管理 `content/` 源文件，发布服务将 manifest/questions/media 编译成只读版本；PostgreSQL 保存索引和版本指针，对象目录保存媒体，运行态数据库只引用 `bank_id + version + question_id`。

**面试追问与证据**

- 追问：题库源文件、发布版本和用户作答为什么不能混在一起？
- 证据：修改草稿不会改变历史 attempt；切换 bank version 后旧结果仍能按 manifest hash 复现。

#### C3. 缺少“用户文档 → 可刷题库”的自动题库工厂

**问题**

直接让一个 LLM 读取整份 PDF 后“生成 50 道题”，会产生上下文截断、题目超出材料、重复题、错误答案、弱干扰项和无法追溯来源等问题；一次调用全部成功也不是真实 workflow。

**改造规划**

生成任务采用可暂停、可重试、可观测的状态机：

```mermaid
flowchart LR
  A[上传文档] --> B[解析/OCR/版面恢复]
  B --> C[结构化切分与知识单元]
  C --> D[知识点/教学目标抽取]
  D --> E[题型与难度规划]
  E --> F[Generator Agent 并行生成]
  F --> G[规则校验]
  G --> H[Judge/Critic Agent]
  H -->|未达标且未超重写预算| I[定向重写]
  I --> G
  H -->|达标| J[Dedup/覆盖率检查]
  J --> K[自动发布版本]
  K --> L[用户刷题反馈]
  L --> M[Repair Agent 修订并回归]
```

**具体技术流程**

1. `Ingestion`：用 PyMuPDF/Docling/Unstructured 解析 PDF、DOCX、PPTX、Markdown；扫描件使用 PaddleOCR；保存页码、标题层级、表格和图像引用。
2. `Chunking`：先按标题/章节/表格边界切 parent，再生成 150—300 中文 token child；每个 child 带 `source_doc_id/page/section/hash/domain/license`。
3. `Knowledge Unit`：抽取 `concept / prerequisite / key_facts / misconceptions / terminology / evidence_spans`，只允许从有定位信息的 evidence span 生成题。
4. `Blueprint`：按用户指定或默认比例生成题型/模态/难度/知识点覆盖矩阵，例如单选 40%、多选 20%、判断 20%、简答 20%；纯文本来源默认生成 `text_only/text_with_context`，只有存在合法图像与视觉教学目标时才生成图文/圈选题。
5. `Generator Agent`：每次只处理一个 knowledge unit，输出严格 `QuestionDraft` schema；正确答案、逐项解析和干扰项误区都必须引用 `evidence_span_ids`。
6. `Rule Gate`：验证 schema、答案数量、选项重复、答案泄露、引用存在、题干自洽、图片是否可用。
7. `Judge/Critic`：独立上下文评估 groundedness、answerability、single-best-answer、distractor quality、teaching value、difficulty match 和 explanation consistency；不读取 Generator 的隐藏推理。
8. `Rewrite`：只把失败维度和证据片段返回 Generator，最多重写 2 次；仍失败则进入 `rejected`，不能无限消耗 token。
9. `Dedup/Coverage`：MinHash/SimHash 做近字面去重，embedding 相似度识别语义重复；覆盖矩阵检查某个知识点或题型是否过密。
10. `Publish`：Demo 策略为规则全通过、Judge 总分 ≥ 0.85、groundedness/answerability 均 ≥ 0.9 即 `auto_approved` 并发布；低分题不拖累整个批次。

**工具/技术栈**

FastAPI + Celery/Dramatiq（后台任务）+ Redis（队列/进度）+ Pydantic（结构化输出）+ PyMuPDF/Docling + PaddleOCR + PostgreSQL + MinIO/本地对象目录 + Qdrant + LangGraph checkpoint。小 Demo 可用 FastAPI `BackgroundTasks` 和 SQLite，但接口保持同一 job contract。

**面试追问与证据**

- 追问：为什么不是一次 Prompt？如何保证题目来自用户文档？
- 证据：展示一个 generation job 的阶段耗时、重写次数、证据 span、Judge 分项、去重结果和发布版本；点击题目可定位原文页码。
- 追问：LLM Judge 自己也会错怎么办？
- 证据：确定性规则 + 双样本一致性/不同 Judge 抽检 + 用户反馈回流；展示 Judge 阈值在 30—50 条标注集上的 precision/recall，而不是只报平均分。

#### C4. Judge 没有量化 Rubric，自动发布无法解释

**改造规划**

Judge 输出必须是结构化对象：

```json
{
  "decision": "pass",
  "scores": {
    "groundedness": 0.96,
    "answerability": 0.94,
    "answer_consistency": 0.92,
    "distractor_quality": 0.86,
    "teaching_value": 0.88,
    "difficulty_match": 0.82
  },
  "blocking_issues": [],
  "rewrite_instructions": [],
  "evidence_span_ids": ["doc01:p12:s3"]
}
```

硬门禁先于总分：引用不存在、答案与解析矛盾、单选多答案、包含材料外结论时直接 fail。Judge prompt、model、temperature、schema、rubric 均版本化；同一题在不同版本的分数可对比。这里的“默认可用”是 Demo 产品策略，不声称等同于专家审核。

**技术流程/栈**

Pydantic `QualityDecision` + 规则校验器 + 独立 Judge provider；Langfuse/OTel 记录 rubric/prompt/model version 和分项 score，PostgreSQL 保存 revision decision。

**面试追问与证据**

- 追问：总分很高但答案引用不存在，能否发布？
- 证据：硬门禁优先于加权总分；准备一条高“教学价值”但 citation 无效的 fail case 和自动重写 trace。

#### C5. 用户发现错题后没有修订闭环

**问题**

“生成完就结束”会让错误题长期留在题库，也错过了一个很适合展示 Agent 在线反馈闭环的技术点。

**改造规划与流程**

用户在题目或解析旁选择“题干不清、答案错误、解析不一致、图片问题、其他”，可附文本或圈选区域：

`feedback → 题目临时标记 disputed → 聚合同类反馈/严重度 → Repair Agent 读取原题、证据和反馈 → 生成 patch → Rule+Judge 回归 → 新 revision → 原 revision 留痕`。

单个低风险反馈先进入 `needs_review`，同一题达到 2 次独立反馈或出现“答案错误”立即从新会话下架；修订通过后自动回到题库。用户可看到“已收到/已修订/未采纳及理由”，后台保留 diff 和回归结果。

**技术流程/栈**

PostgreSQL `question_feedback/question_revisions` + job queue + JSON Patch/结构化 diff + Rule/Judge regression；同一用户重复反馈通过 `(user_id, question_id, revision, category)` 幂等去重。

**面试追问与证据**

- 追问：线上反馈如何防止恶意或噪声污染题库？
- 证据：反馈类型、用户去重、置信度、下架阈值、Repair diff、回归测试以及新旧 revision 的可追溯链。

### D. 题目数据契约（后续必须按此执行）

#### D1. 题库 manifest

**改造规划**

每个题库发布单元必须有独立 manifest，明确领域、受众、来源策略、生成/Judge 版本、状态和默认练习模式：

```yaml
bank_id: stomach-teaching
version: 0.1.0
title: 胃部内镜基础观察题库
body_part: stomach
audience: 消化内镜研修医
language: zh-CN
status: draft
question_count: 12
source_policy: public_or_original_only
publish_policy: rule_gate_and_llm_judge
judge_rubric_version: question-quality-v1
generator_version: qgen-v1
default_modes: [practice, review]
```

**技术流程/栈与面试追问/证据**

YAML + Pydantic Settings/Schema 在 CI 和发布接口双重校验；面试展示 manifest hash 如何绑定 questions/media，并证明题量、Judge 版本或来源变化会产生新版本。

#### D2. JSONL 题目格式

**改造规划**

以一行一题的 JSONL 作为内部内容真源，显式表达题型、模态、知识点、答案、Rubric、逐项解析、来源和生成质量信息：

```json
{
  "question_id": "stomach_lesion_single_001",
  "bank_id": "stomach-teaching",
  "case_id": "case_stomach_001",
  "note_id": "note_stomach_mucosa_001",
  "type": "single_choice",
  "modality": "image_text",
  "body_part": "stomach",
  "topic": "病变观察",
  "knowledge_points": ["黏膜颜色", "观察与诊断边界"],
  "difficulty": "basic",
  "stem": "根据图像和题干资料，最合适的观察描述是？",
  "media": [{"kind": "image", "path": "media/stomach_001.jpg", "alt": "胃部公开教学图像"}],
  "options": [
    {"id": "A", "text": "可见局部黏膜颜色改变", "is_correct": true, "misconception": null},
    {"id": "B", "text": "仅凭单帧图像即可确定最终诊断", "is_correct": false, "misconception": "过度诊断"}
  ],
  "answer": {"kind": "option_ids", "value": ["A"]},
  "rubric": {"facts": ["颜色改变"], "forbidden_claims": ["最终诊断", "治疗方案"]},
  "explanation": {"summary": "先描述可见事实，再区分诊断结论。", "per_option": {"A": "覆盖题目考点", "B": "超出图像证据"}},
  "references": [{"source_id": "kb_stomach_001", "locator": "§2.1", "license": "..."}],
  "tags": ["胃", "病变观察", "基础"],
  "status": "auto_approved",
  "generation": {"source": "generator_agent", "prompt_version": "qgen-v1", "evidence_span_ids": ["kb_stomach_001:s2.1"]},
  "quality": {"judge_version": "question-quality-v1", "score": 0.91, "decision": "pass", "revision": 1}
}
```

**技术流程/栈与面试追问/证据**

Pydantic discriminated union 生成 JSON Schema 和前端 TypeScript 类型；面试现场分别载入 `text_only single_choice`、`image_text single_choice` 和 `short_answer`，证明共用核心字段但走不同 renderer/grader。

#### D3. 校验规则

**改造规划与技术流程/栈**

- 题型和答案结构必须匹配：单选只能一个 `option_id`，多选至少两个，判断必须是 boolean。
- `text_only/text_with_context` 允许 `media=[]`；`image_text/image_hotspot/multi_image` 必须有满足数量和类型约束的 media，不能用占位图绕过校验。
- 选项 ID 不重复；正确答案不能出现在题干的显著提示中。
- 简答题必须有 `rubric.facts`、`forbidden_claims` 和至少一个参考资料。
- 每张图像必须有来源、license/citation、尺寸检查和 alt 文本。
- `status=published` 必须有通过的确定性校验和 Judge 记录；人工审核作为可选 `expert_reviewed` 等级，不阻塞 Demo 自动发布。
- 自动生成题必须能定位到原文 `evidence_span_ids`，并记录 generator/judge/prompt/model 版本。
- benchmark 题不能自动混入教学题库；用户反馈打回后旧 revision 不再进入新练习，但保留审计链。

规则以 `QuestionValidatorRegistry` 分成通用、题型、模态、领域和发布门禁五层；错误返回稳定 `code/path/message/suggested_fix`，供前端定位到具体行和字段。

**面试追问与证据**

- 追问：schema 合法是否代表题目质量合格？
- 证据：schema 只保证结构；规则门禁、Judge 和用户反馈分别负责确定性语义、生成质量和线上纠错，展示三层各自拦截的样例。

### E. 练习引擎和学习业务

#### E1. 没有标准刷题会话状态

**问题**

当前运行一次 Agent 就结束，缺少考试模式、题号导航、标记、暂停、提交锁定、结果复盘等刷题软件的基本状态。

**改造规划**

实现三种模式：

- **练习模式**：提交后立即讲解，可请求提示。
- **测验模式**：先完成一组题，结束后统一查看答案和解析。
- **自适应模式**：由 Agent 根据到期复习、薄弱知识点和题型覆盖选择下一题。

会话支持题号 palette、标记、收藏、置信度（不确定/一般/确定）、暂停和重新开始。

**技术流程/栈**

前端 `PracticeSessionState`；后端 `practice_sessions`、`attempts`、`question_flags`；提交接口幂等键 `session_id + question_id + attempt_no`；SSE 只用于 Agent 讲解，不用于客观题基本提交。

**面试追问与证据**

- 追问：如何避免重复点击造成重复作答？
- 证据：按钮 loading/禁用、后端幂等键、重复请求返回同一 attempt，不增加复习次数。

#### E2. 复习算法过于简化

**问题**

“答错后隔一天”可以做 demo，但不能作为可吹的完整记忆算法，也不能体现 Anki/FSRS 的思路。

**改造规划**

先实现可解释的 FSRS-inspired 调度字段，再根据时间允许程度接入开源 `fsrs` 实现：

```text
card_state: new / learning / review / relearning / suspended
stability, difficulty, retrievability
reps, lapses, last_review_at, due_at
rating: again / hard / good / easy
```

同一 note 生成的 sibling cards 默认不连续出现；到期题优先，过期积压时限制新题数量。页面显示“下次复习：今天/明天/3 天后”，不直接向普通用户展示公式。

**技术流程/栈**

`attempt + confidence + rating → scheduler → card_state update → due queue`。使用 Python `fsrs` 或官方实现时锁定版本；没有足够真实复习日志时，不声称“算法效果提升”，只展示可复现调度结果。

**面试追问与证据**

- 追问：FSRS 与固定间隔有什么区别？
- 证据：同一张卡用 Again/Hard/Good/Easy 产生不同 stability/due_at；对照表展示工作量和目标保留率。

#### E3. 错题本不是知识点复习队列

**问题**

当前错题更多是“某个病例待复盘”，无法回答“我为什么错、错在胃部位定位还是病变属性、下一道应该练什么”。

**改造规划**

每次作答生成 `error_event`：

```text
question_id, knowledge_point_id, error_tags,
selected_answer, expected_answer, confidence,
missed_facts, contradiction_flags, next_action
```

错题页按知识点聚合，支持“只练我最近三次错在部位定位的题”。

**技术流程/栈**

`GradeResult → ErrorClassifier(rule + optional LLM) → error_event → mastery aggregator → FSRS queue`；事件 append-only，聚合画像可重算。

**面试追问与证据**

- 追问：错题删除后是否丢失历史？
- 证据：答对只改变当前复习状态，不删除历史 event；按知识点重放 events 可还原趋势。

### F. Agent 角色和工具调用

#### F1. Agent 只是一次固定运行，不像陪练老师

**问题**

固定三工具能展示工程步骤，但不能体现 Agent 根据用户行为做决策。比如用户只想要提示时，不应先跑完整评分和记忆更新。

**改造规划**

定义一个面向用户的 **内镜研修 Tutor Agent**，内部用 routing + bounded workflow：

| 用户意图 | Agent 动作 | 是否写入长期状态 |
|---|---|---|
| “给我一点提示” | 读取当前题和薄弱知识点，生成不泄露答案的观察提示 | 否 |
| “解释 B 为什么错” | 读取该选项的 misconception 和 KB 证据 | 否 |
| “提交答案” | 判分、召回资料、生成逐项解析 | 是，提交后 |
| “我总是错在胃部位定位” | 查询长期画像和错题事件，安排专题训练 | 是，生成计划 |
| “帮我做一张卡” | 从讲解生成 note/card 草稿，等待用户确认 | 用户确认后 |
| “评测我的模型” | 交给独立评测服务，不把 API key 放进记忆 | 否 |

**建议工具清单**

```text
select_next_question
get_question_context
give_hint_without_answer
retrieve_teaching_evidence
grade_objective_answer
grade_open_answer
explain_option
record_attempt
update_mastery
schedule_review
create_flashcard_draft
run_model_eval
write_trace
```

**技术流程/栈**

LangGraph state graph（或等价自研状态图）+ Pydantic tool schema + FastAPI；每个 tool 都有 timeout、retry policy、idempotency key 和 typed result。开发详情写入 Langfuse/OpenTelemetry trace，用户主界面只显示“提示/讲解/复习已更新”。

**面试追问与证据**

- 追问：哪里体现了 Agent，而不是 Chatbot？
- 证据：同一会话中，用户请求“提示”和“提交”会触发不同工具子图；Agent 根据结果决定是否进入复习更新或请求人工确认。

#### F2. Tool/Workflow 术语泄漏给普通用户

**问题**

`Plan`、`Act`、`Recovery`、`Receipt`、`Memory Delta` 对工程师有意义，对研修医不友好。

**改造规划**

建立 UI 语言映射：

| 内部字段 | 用户默认文案 | 高级详情文案 |
|---|---|---|
| Plan | 正在准备本题 | Plan |
| Retrieve | 正在查找相关知识点 | Knowledge Retrieval |
| Grader | 正在核对你的答案 | Grader |
| Memory | 已更新本题掌握度 | Memory Update |
| Retry | 正在重新尝试 | Retry / Recovery |
| Trace | 本次学习记录 | Trace |

主流程只展示 3—4 个进度步骤；完整 JSON、工具名、调用 ID 放入“查看运行详情”抽屉。

**技术流程/栈**

后端统一输出 typed event，前端 `EventPresenter` 将内部事件映射为用户文案；高级抽屉按权限读取 trace summary，而不是直接渲染原始日志。

**面试追问与证据**

- 追问：隐藏术语会不会失去 Agent 可观测性？
- 证据：同一 event stream 在用户层呈现人话状态、在开发层呈现 tool/span；两者共享 event id，可互相定位。

#### F3. Tutor 只能提交后出现，没有进入用户思考过程

**问题**

刷题中的困难发生在提交之前：看不懂术语、两个选项犹豫、不会观察图像、想要一点提示。把 Agent 限制为提交后的评分器，用户自然感受不到“智能陪练”。

**改造规划**

刷题页使用可收起的 **Tutor Sidecar**：桌面端右侧 360—420px，移动端为底部全屏抽屉；不遮挡题干和选项。预置操作包括“给一点提示”“解释这个术语”“比较我选中的两个选项”“引导我观察图片”“我想追问”。用户可以引用当前选项、选中文字，或在图像上框选区域后提问。

Tutor 不是无上下文 LLM，也不是每句话都跑完整 RAG，而是混合路由：

```text
用户消息 + current_question + selection + hint_level + learner_snapshot
  → 轻量意图路由
  ├─ 术语/固定选项解释：题目数据工具，通常不调检索
  ├─ 当前题提示：题目 rubric + 已请求提示，禁止读取/输出 answer key
  ├─ 知识点追问：metadata-filtered hybrid RAG → rerank → 引用回答
  ├─ 图像圈选：region crop/坐标 + VLM（可用时）+ 题目绑定证据
  ├─ 学习计划问题：handoff Mentor
  └─ 提交后复盘：grader result + evidence → 逐项解释
```

**分级提示**

- L1 观察方向：告诉用户先看哪里，不出现答案或关键实体。
- L2 概念提醒：提示相关知识点和区分维度。
- L3 排除法：解释用户选中的一个干扰项为什么值得怀疑，仍不直接报正确选项。
- 提交后才开放完整答案和逐项解析；`hint_level` 和使用次数进入 attempt，用于分析提示依赖。

**性能目标与工程手段**

| 场景 | 目标 | 主要手段 |
|---|---:|---|
| 固定术语/选项解释 | P95 完整响应 < 800ms | 本地题目索引、模板缓存、不调用大模型 |
| 普通知识追问 | P95 TTFT < 1.5s，完整回答 < 6s | SSE、检索与画像读取并行、top-k 限制、prompt 缓存 |
| 图像/VLM 追问 | P95 TTFT < 2.5s，完整回答 < 10s | 先流式状态、图像缩放/region crop、超时和取消 |
| Provider 故障 | 8s 超时，最多 1 次可控重试 | circuit breaker；fallback 明确标注且不冒充真实模型 |

对话支持取消、重试和继续编辑；SSE 事件为 `message_start/token/source/tool_status/message_end/error`。前端只显示“正在查找本题知识点”“已找到 3 条资料”等可理解状态。**不展示原始 chain-of-thought**；只显示由实际 tool/trace 生成的计划摘要、来源、耗时和可验证解释。

**工具/技术栈**

React sidecar + SSE（FastAPI `StreamingResponse`）+ 自研 event protocol；Qdrant hybrid retrieval；LiteLLM provider adapter；可参考 CopilotKit AG-UI/AI Elements 的 message parts、tool status、sources、attachment 和 cancel 交互，但不为此迁移现有前端框架。

**面试追问与证据**

- 追问：怎样避免 Tutor 在提交前泄露答案？
- 证据：answer key 不进入 pre-submit context；三个提示级别有 snapshot regression，统计 answer leakage rate。
- 追问：为什么延迟能降低？
- 证据：按 `route/retrieval/model/render` 拆分 P50/P95，展示 cache、并行读取、小模型路由前后的对照。

#### F4. 多 Agent 不能只靠名字，必须有不同职责和上下文边界

**改造规划：前台双角色，后台职责型 Agent**

| Agent/组件 | 何时触发 | 可见上下文 | 专属工具 | Memory scope | 结构化输出 |
|---|---|---|---|---|---|
| **Tutor Agent** | 当前题提示、术语、追问、提交后讲解 | 当前题、用户选择、已用提示、相关 KB、少量画像 | `get_question_context/retrieve_evidence/explain_option/give_hint` | 当前会话；只读长期画像 | `TutorMessage{answer,sources,hint_level,next_actions}` |
| **Mentor Agent** | 今日计划、薄弱项、跨会话复习 | 聚合 attempts、mastery、FSRS due、用户目标；默认不看完整聊天 | `query_mastery/build_study_plan/schedule_review` | 跨会话长期画像 | `StudyPlan{goals,items,reasons,due}` |
| **Generator Agent** | 用户导入文档或新增领域 | 单个 knowledge unit、evidence spans、blueprint、题型模板 | `load_spans/create_draft/generate_distractors` | 生成 job；不读学员画像 | `QuestionDraft` |
| **Judge/Critic Agent** | 每个题目草稿/修订 | 草稿、证据、rubric；不看 Generator 隐藏推理 | `verify_citations/grade_rubric/request_rewrite` | 当前 revision | `QualityDecision` |
| **Repair Agent** | 用户反馈或回归失败 | 原题 revision、证据、反馈聚合、失败维度 | `create_patch/run_rule_gate/run_regression` | 题目版本历史 | `QuestionPatch` |
| **Evaluation Agent** | 用户 BYOK 模型评测 | 冻结 manifest、模型原始输出、server-only answer key | `invoke_candidate/parse_output/score_case/aggregate` | 单次 eval run | `EvalArtifact` |
| **Indexer/Retriever** | 文档入库/检索 | 文档 chunk 或 query | parser/embed/index/search/rerank | 索引版本 | 普通 service result，不称 Agent |

每个 Agent 都有独立的 `system_prompt_version / allowed_tools / input_schema / output_schema / max_steps / token_budget / timeout / memory_policy`。Prompt 不散落在 Python 字符串里，按 `prompts/{agent}/{version}.yaml` 版本化并绑定 trace。

**技术流程/栈与编排取舍**

- 用户始终与 Tutor 或 Mentor 对话；Generator/Judge/Repair/Evaluation 不直接抢占前台会话。
- 前台“今天该学什么”是明确领域切换，采用 handoff 到 Mentor；“请校验这道题”是 bounded subtask，采用 agent-as-tool 后控制权返回 Generator workflow。
- 题库生成使用代码定义的 state graph：解析、校验、发布由确定性代码控制，只有生成和质量判断节点是 Agent。
- Generator 与 Judge 不共享隐藏思考，只共享 schema 和证据；Repair 在新 revision 工作，避免原地覆盖。
- 不使用 round-robin 群聊或所有 Agent 共享全量 history，避免 token 成本、提示污染和难复现。

**面试追问与证据**

- 追问：为什么这里需要多 Agent，而不是一个 Prompt 加角色字段？
- 证据：职责之间存在不同工具权限、context/memory 和独立验收；展示 Tutor 无权发布题库、Generator 无权读取用户 API key 的权限测试。
- 追问：什么时候退化为单 Agent？
- 证据：普通提示/讲解由 Tutor 单 Agent + tools 完成；只有生成—批判闭环、跨会话 Mentor 和独立模型评测才拆分。

#### F5. “自研 Agent”与框架使用边界不清

**改造规划：框架比较与本项目结论**

| 方案 | 优点 | 当前项目问题 | 结论 |
|---|---|---|---|
| LangChain/LangGraph | 状态图、checkpoint、stream、interrupt、生态完整 | 若全量使用，面试中容易只会讲框架节点 | **仅用 LangGraph 做复杂 job 的持久状态图/checkpoint** |
| OpenAI Agents SDK | tools、handoff、agents-as-tools、session、trace 简洁 | 偏 OpenAI provider，BYOK/本地模型需额外适配 | 作为模式参考或 OpenAI adapter，不做核心运行时 |
| AutoGen | team/selector/swarm/事件模型丰富 | 群聊式协作对固定题库流程成本高、可控性弱 | 不选主框架 |
| CrewAI | role/task/crew 和 Flow 易于快速演示 | 与自研 runtime/已有 FastAPI 抽象重叠 | 不选主框架 |
| Semantic Kernel | .NET/企业微软生态好 | 当前是 Python/FastAPI，收益低 | 不选 |
| PydanticAI | 类型安全、依赖注入、structured output、轻量 delegation | durable graph 仍需自己补或接其他组件 | 借鉴/可用于 typed agent wrapper |
| 自研 run loop | 可讲清状态、预算、工具、失败恢复和 trace | 需要自己承担边界测试 | **核心方案** |

**最终推荐：Hybrid Harness**

自研以下核心，保证简历中的“Agent Runtime”有真实实现：

```text
AgentSpec            # prompt/model/tools/output/memory/budget policy
RunContextBuilder    # 按当前题、角色、权限构造最小上下文
RunLoop              # model → tool call → result → next step/final
TypedToolRegistry    # Pydantic input/output、权限、timeout、idempotency
StateEventBus        # append-only run/tool/model/retrieval/memory events
BudgetController     # max_steps/token/cost/deadline/cancel
RetryPolicy          # error taxonomy、退避、circuit breaker
CheckpointStore      # checkpoint/resume、避免重复 side effect
MemoryWriteGate      # session/event/profile 的晋升与撤销
ProviderAdapter      # LiteLLM/OpenAI-compatible/vLLM/Ollama
TraceExporter        # OpenTelemetry/Langfuse
```

外部组件只解决非差异化能力：LiteLLM 做 provider 兼容；Qdrant 做 hybrid retrieval；Langfuse/OTel 做 trace/eval；LangGraph 只承载题库生成/Repair 等长流程 checkpoint。Tutor 的短 run loop 自研，避免为了 1—3 次工具调用引入复杂图。

**技术流程/栈：运行协议**

```text
RunCreated → ContextBuilt → ModelRequested
→ ToolProposed → ToolValidated → ToolStarted → ToolSucceeded/Failed
→ ModelResumed → OutputValidated → MemoryProposed → MemoryCommitted
→ RunCompleted/TimedOut/Cancelled
```

所有副作用工具必须有 `idempotency_key`；恢复时重放 event 但不重复 `record_attempt/publish_bank/run_candidate_model`。这比页面上写 `Plan/Act` 更能回答 Agent 工程面试。

**面试追问与证据**

- 追问：为什么不全用 LangGraph？
- 证据：Tutor run loop 的代码和单元测试可独立运行；复杂生成 job 再使用 checkpoint graph，并比较两类流程的复杂度。
- 追问：Agent 崩溃后怎么恢复？
- 证据：在 Judge 后注入进程中断，恢复后从 checkpoint 继续且不重复生成/发布；trace 中可看到同一 run 的 resume 事件。

### G. 评分和讲解

#### G1. 客观题评分不能依赖字符串比较

**问题**

单选/判断可以精确判分，多选如果把整串答案拼接比较会误判部分正确；排序、匹配、数值题也需要独立规则。

**改造规划**

按题型实现 grader registry：

| 题型 | 评分规则 |
|---|---|
| 单选 | `selected_id == correct_id` |
| 多选 | set precision/recall/F1；可配置全对或部分得分 |
| 判断 | boolean exact match |
| 匹配 | 每个 pair 独立得分，总分归一化 |
| 填空 | 规范化、同义词、大小写和单位规则 |
| 数值 | 容差区间和单位换算 |
| 图像热点 | 框/点与标注 IoU 或距离阈值 |

**技术流程/栈**

`grader_registry[type].grade(submission, answer_key, rubric) → GradeResult`；结果包含 `score`, `correctness`, `partial_credit`, `mistakes`, `explanation_refs`，禁止用一套字符串逻辑处理所有题型。

**面试追问与证据**

- 追问：多选部分得分如何避免“全选也高分”？
- 证据：展示 set precision/recall/F1 与误选惩罚的边界用例；同一输入在 grader 单测中得到固定结果。

#### G2. 开放题评分没有明确 Rubric

**问题**

当前开放题主要是事实别名命中，无法处理同义表达、遗漏、互相矛盾、没有证据支撑或过度诊断。

**改造规划**

采用“规则优先，LLM judge 二次判断”的分层评分：

1. **结构化抽取**：把答案拆成 `body_part / finding / attribute / count / evidence / uncertainty`。
2. **事实覆盖**：对照题目 Rubric 的 atomic facts，计算 coverage。
3. **矛盾和越界**：检查是否把“观察所见”写成“最终诊断/治疗方案”。
4. **知识库核验**：只允许使用题目绑定的教学证据，不把 benchmark 答案直接塞回 prompt。
5. **LLM judge**：在固定 Rubric、正反例和证据片段下输出 JSON；低置信度则标记“需要用户确认/暂不给确定分数”。

计划评分示例：

```text
score = 0.45 * fact_coverage
      + 0.25 * evidence_groundedness
      + 0.20 * answer_relevance
      + 0.10 * safe_expression
      - contradiction_penalty
```

这个公式在实现时需要用 20—30 条人工标注样本校准，不能在没有校准前声称客观有效。

**技术流程/栈**

Pydantic structured output；中文医学同义词词表；`bge-m3`/同类 embedding 做语义相似；`bge-reranker-v2-m3` 或 Cohere multilingual rerank 做候选判断；LLM judge 仅作为第二层，不替代确定性客观题 grader。

**面试追问与证据**

- 追问：为什么不能只用 embedding 相似度？
- 证据：展示一个“词面相似但漏掉关键事实”的反例，以及“表达不同但事实完整”的正例；同时保存规则层和 judge 层的中间结果。

#### G3. 讲解只给总评，没有逐选项、错因和下一步

**问题**

用户刷题最需要的是“为什么错”和“下次怎么做”，不是一段泛泛的总结。

**改造规划**

结果页固定四块：

1. 结果：正确/部分正确/需要复习。
2. 逐项解析：每个选项为什么对/错，引用题目绑定的知识片段。
3. 错因标签：部位混淆、漏掉阴性信息、数量遗漏、观察越界等。
4. 下一步：再练一题、加入复习卡、查看该知识点讲义。

Agent 不在提交前泄露正确答案；提示分为“观察路径提示”和“关键概念提示”，每次提示都记录是否泄露答案的回归测试。

**技术流程/栈**

`GradeResult + option rationales + retrieved evidence + learner error tags → ExplanationSchema → React result blocks`；引用片段与 `question_id/bank_version` 绑定。

**面试追问与证据**

- 追问：如何避免模型生成一段看似合理但与选项无关的讲解？
- 证据：每个 option 必须返回 rationale 和 evidence ids；缺少引用或与答案键矛盾时 schema/Judge 失败。

### H. 题库知识库 RAG

#### H1. 当前没有真正的题库向量知识库

**问题**

当前检索 corpus 主要来自 5 个 portfolio case 的 facts，能做可解释小样本匹配，但不是“题库/讲义/参考资料的 RAG”。

**改造规划**

建立三类 collection 或带 `corpus_type` 的统一 collection：

- `question_explanation`：题干、选项解析、易错点。
- `teaching_note`：解剖、病变观察、术语、报告规范教学资料。
- `learner_memory`：经过用户确认或稳定统计后的知识点记忆。

评测集和教学库隔离；答案 key 只在提交后评分服务可见。

**技术流程/栈**

Qdrant collection alias 按 `domain/corpus/version` 隔离；索引 job 生成 chunk manifest，Tutor 通过 metadata filter 检索，评分服务通过受限 repository 读取 answer key。

**面试追问与证据**

- 追问：为什么 learner memory 不应和公开知识库无条件混检？
- 证据：展示 corpus filter 和权限测试；用户画像只影响个性化提示，不作为医学事实证据。

#### H2. chunk、metadata 和混合检索没有设计

**问题**

如果把一整篇讲义塞进一个向量，召回粒度太粗；如果只切成无上下文的小句，又无法讲清楚医学概念。

**改造规划**

采用 parent-child chunk：

- Markdown 标题/小节优先切分。
- child chunk：约 150—300 中文 token，重叠 40—80 token。
- parent chunk：一个完整知识点或一个题目解析小节。
- 每个 chunk 保留 `source_id/version/title/body_part/topic/knowledge_point/question_ids/license/locator`。

**检索流程**

```text
用户问题/当前题目
  → 意图识别和 metadata filter
  → dense top-20（语义）
  + sparse top-20（BM25/关键词）
  → RRF 或加权融合
  → rerank top-10
  → 阈值过滤和 parent 回填
  → 取 top-3~4 片段给 grader/tutor
  → 返回 evidence_id、来源标题、章节和可读引用
```

**技术流程/栈**

Qdrant（dense+sparse named vectors）+ `bge-m3`/本地 embedding + BM25/fastembed sparse + `bge-reranker-v2-m3`；小型 Demo 可用 Qdrant local/embedded，不必一开始部署复杂集群。

**面试追问与证据**

- 追问：为什么要 hybrid search？
- 证据：精确术语/题号由 sparse 召回，语义改写由 dense 召回，使用 RRF 后通过 Recall@K、MRR/nDCG 对比只用 BM25 和只用向量的结果。

#### H3. RAG 质量没有离线评测

**问题**

没有证据说明 chunk、top-k、rerank 是否真的改善了讲解；仅展示“检索返回 5 条”不够。

**改造规划**

构造 30—50 条检索 query，覆盖部位、知识点、同义词、错因和模糊问法，人工标注相关 chunk。评测：

- Retrieval：Recall@K、MRR、nDCG、Context Precision、Context Recall。
- Generation：Answer Relevancy、Faithfulness、引用命中率、无依据陈述率。
- Agent：Tool Call Accuracy、任务完成率、平均工具次数、失败恢复率。

结果页显示样本数、数据集版本和置信区间；不把固定 Golden Case 的 100% 叫作开放域准确率。

**技术流程/栈**

Pytest/自研 eval runner 读取冻结 query—relevant_chunk 数据集；Ragas/自定义指标计算生成质量，Langfuse Experiment 对比不同 chunk、top-k 和 reranker 版本。

**面试追问与证据**

- 追问：为什么 rerank 后 Recall@K 可能下降但最终回答变好？
- 证据：同时报告候选召回、最终 context precision/recall 和 faithfulness，并保留逐 query 差异而非只看均值。

### I. 短期记忆、长期记忆和带教 Agent

#### I1. 记忆概念不清，Memory 只是一次运行结果

**问题**

当前的 Memory 更像一次运行的画像 Delta，不能解释“这位研修医过去一周在哪些知识点持续出错”。

**改造规划**

采用四层记忆：

| 层级 | 生命周期 | 内容 | 存储 |
|---|---|---|---|
| 对话记忆 | 当前回答 | 最近几轮对话、当前问题和已请求提示 | session state/短期缓存 |
| 任务记忆 | 当前练习会话 | 题号、选项、提示次数、工具结果、是否提交 | PostgreSQL/Redis TTL |
| 作答事件 | 长期事实 | 每次题目作答、置信度、错因、评分、耗时 | `attempts`、`error_events` |
| 学习画像/长期记忆 | 跨会话 | 知识点掌握度、稳定薄弱项、偏好和复习卡状态 | `learner_profile` + 可选向量索引 |

只有提交成功、用户确认或多次重复出现的事实才晋升为长期记忆；不保存原始 chain-of-thought，不把 API key、患者信息或未经确认的医学判断写进 memory。

**技术流程/栈**

`attempt event → memory extractor → dedupe/confidence gate → mastery update → FSRS scheduler`。可参考 [Mem0 的 conversation/session/user memory 分层](https://docs.mem0.ai/core-concepts/memory-types)，Demo 先用 PostgreSQL/SQLite 实现同样的分层，后续再接 Mem0/OpenMemory。

**面试追问与证据**

- 追问：短期和长期记忆如何避免互相污染？
- 证据：新会话只取当前题和相关画像；复盘后删除 session，不影响长期掌握度；用户可以撤销一次画像更新。

#### I2. 带教 Agent 没有长期计划

**改造规划**

增加“我的研修画像”页：知识点掌握度、近 7 天趋势、错因分布、到期复习、下一周建议。带教 Agent 可以回答“我今天先练什么”，但建议必须引用作答事件和题库知识点，不凭空生成学习计划。

**技术流程/栈**

`attempt/error_event/FSRS due → deterministic feature aggregation → Mentor Agent tool call → StudyPlan schema`；PostgreSQL 保存画像与计划版本，Mentor 只读原始事件并通过工具提交计划。

**面试追问与证据**

- 追问：Mentor 与 Tutor 的记忆和职责有什么不同？
- 证据：Tutor 只看当前题和少量画像，Mentor 看跨会话聚合且不读取 answer key/完整聊天；展示两份 AgentSpec。

### J. 用户自定义模型 API 与评测实验室

#### J1. 当前评测入口不完整，不能证明真实调用

**问题**

后端已有自定义评测函数，但用户界面不能选择 API、模型、评测集，也不能判断“到底有没有发出请求”。如果没有真实调用，就不能把结果写成模型评测。

**改造规划**

评测页分为四步：

1. 选择评测集：教学小集、冻结 benchmark holdout、用户上传集。
2. 输入连接信息：Provider 类型、OpenAI-compatible base URL、model、一次性 API key；默认不持久化，页面提示不会写入日志。
3. 预览请求：显示样本数、图像数、题型、答案不会发送给模型、预计调用次数。
4. 开始评测：明确显示 `未调用 / 调用中 / 已完成 / 部分失败`，逐题展示模型原始回答摘要、解析结果、评分理由、延迟和错误。

**技术流程/栈**

统一 `ModelAdapter` 接口：OpenAI-compatible、vLLM、Ollama、DashScope 等适配到同一请求结构。可用 [LiteLLM](https://docs.litellm.ai/) 做 provider 路由、重试、fallback、成本和限流，但不能把 fallback 的结果标成被测模型结果。

API key 只存在请求生命周期内的后端内存或短时 secret store：不写数据库、不写 trace、不出现在异常日志；用户离开评测页立即清理。

**面试追问与证据**

- 追问：候选模型超时后可以换成平台模型完成评测吗？
- 证据：不能；artifact 将该样本标为 candidate timeout。Provider fallback 只用于 Tutor 可用性，不用于被测模型。

#### J2. BaseCase 选择不透明

**改造规划**

每个评测集有不可变 manifest：

```yaml
eval_set_id: endoscopy-mini-v1
purpose: model_eval
split: test
cases:
  - id: e001
    image: public/endo_001.jpg
    tasks: [organ_recognition, abnormality_presence]
  - id: e002
    image: public/endo_002.jpg
    tasks: [counting, spatial_reasoning]
answer_key: server_only
version_hash: sha256:...
```

默认采用分层抽样：按部位、题型、难度、是否开放题覆盖；用户也可手选 3/5/10 个样本。开始后锁定 manifest，避免中途换题。

**技术流程/栈**

`EvalSetRegistry → stratified sampler → immutable run manifest → answer-key service`；manifest 与 `sha256/code_commit/prompt_version` 写入 artifact，前端只在 run 前允许修改选择。

**面试追问与证据**

- 追问：用户手选样本后还能和其他模型公平比较吗？
- 证据：只在相同 manifest hash 上横向比较；自选 run 单独标识，不混入固定榜单。

#### J3. 模型评测指标不应只有“总分”

**改造规划与计划指标**

- 单选/判断：Exact Accuracy。
- 多选：set F1、漏选率、误选率。
- 简答：Rubric score、事实覆盖、无依据陈述率。
- 结构化输出：JSON parse rate、schema violation rate。
- 视觉能力：部位、病变属性、数量、空间位置分别统计。
- Agent 能力：工具选择准确率、工具参数合法率、任务完成率、重试后成功率。
- 工程指标：P50/P95 latency、token、成本、超时率、provider error rate。

小样本只报告 `正确数/总数` 和区间，不写“已证明泛化能力”。

**技术流程/栈**

类型化 scorer registry 对客观题、开放题、结构化输出、视觉任务和 Agent tool trace 分别评分；Pandas/Polars 聚合，artifact 以 JSONL + summary JSON + HTML/前端图表展示。

**面试追问与证据**

- 追问：总分如何加权？
- 证据：先展示各维度原始指标和样本数，再由 versioned metric config 计算综合分；改变权重会生成新 metric version，不覆盖旧结果。

### K. 前端信息架构和用户体验

#### K1. 一页塞太多开发信息

**改造规划**

最终页面结构：

1. **研修首页**：今日计划、部位题库、题型筛选、待复习和错题入口。
2. **刷题会话页**：图像/题干/选项/进度/提示/标记；默认全屏聚焦。
3. **结果复盘页**：逐项解析、知识点、错因、下次复习和下一题。
4. **我的画像**：掌握度、复习日历、错因趋势、带教建议。
5. **题库管理**：创建、导入、校验、草稿、发布版本。
6. **模型评测**：独立入口，面向求职展示和工程人员。

Agent trace、API 连接状态、原始 JSON、评测 artifact 进入抽屉/二级页，不进入刷题首屏。

**技术流程/栈与面试追问/证据**

React Router 保留可深链页面，Zustand/React Query 管理会话与异步状态；用三分钟录屏证明用户只经“选题—作答—Tutor—复习”完成主任务，高级 trace 不占首屏。

#### K2. 图片尺寸和视觉层级不稳定

**改造规划**

- 主图统一 4:3 或原图比例容器，`object-fit: contain`，不拉伸。
- 所有题卡缩略图使用相同 aspect-ratio；原图查看支持放大、缩小、适应窗口。
- 图像加载中显示 skeleton，失败显示“图像暂不可用 + 继续答题/重试”。
- 主图下只保留来源、用途和 alt；不把内部文件名当作用户文案。
- 移动端图像优先，选项固定在图像下方；不因右侧 Agent 面板造成横向滚动。

**技术流程/栈与面试追问/证据**

CSS `aspect-ratio` + `object-fit: contain` + ResizeObserver + 图片 metadata；Playwright 截图比较多种原图比例与三档视口，证明无裁切、拉伸和布局跳动。纯文本题不渲染空图片容器。

#### K3. 医疗边界要保留，但不能用防御性术语淹没页面

**改造规划**

主界面使用一句短提示：

> 本平台用于教学练习；图像和讲解仅供研修及医生复核前参考，不替代正式诊断。

具体来源、生成/Judge 状态、模型是否真实调用、评测集版本进入“查看详情”。安全检查失败时用人话说明“这段回答超出了当前图像能支持的范围，请改成观察描述”。

**技术流程/栈与面试追问/证据**

领域包提供 `ui_terms` 和最短提示，底层 policy 返回机器码，前端映射成人话；截图对比普通用户层与高级来源详情，证明边界保留但不喧宾夺主。

#### K4. 交互状态不完整

**改造规划**

每个页面必须覆盖：加载、空数据、提交中、成功、部分成功、超时、重试、无权限、题库未发布、评测未调用、评测部分失败。按钮必须防重复提交，错误靠近发生位置，键盘和移动端触控目标不少于 44px。

**技术流程/栈与面试追问/证据**

为 query/mutation/job/stream 定义统一状态机，MSW/故障注入覆盖 timeout、partial、disconnect；Playwright 证明重复点击只产生一个 request_id，断线后可以恢复或取消。

#### K5. Agent UI 应服务刷题，而不是把聊天框贴在页面旁边

**改造规划：推荐布局**

- 默认首屏 70% 以上空间用于图像/题干/选项/进度，Tutor 以侧边按钮和一行建议存在，不抢答题注意力。
- 展开 Tutor 后，当前题、选中选项和圈选图像自动成为上下文；用户不需要重复描述“我在问哪一题”。
- tool 状态用“正在查找本题资料/正在比较两个选项/已更新复习计划”，来源用可展开引用卡；`dense_score/tool_args/run_id` 只在开发者详情显示。
- streaming 时显示可取消状态；超时后保留已输出文本并给“继续/换简短回答”，不能让整个练习页卡死。
- 生成题库页用 job progress 展示“解析 12/20 页、已生成 34 题、7 题正在重写、2 题未通过”，而不是瞬间全绿。
- 用户反馈入口紧邻题干/解析，支持原因标签、补充说明和图像圈选；提交后明确显示处理状态。

**不展示的内容**

原始 chain-of-thought、完整 system prompt、API key、内部变量名、向量分数、长 JSON、所有 Agent 之间的消息。普通用户只看到结论、简短可验证理由、引用、工具阶段和下一步动作。

**验收证据**

同一页面录制三段行为：未展开 Tutor 的专注刷题、边做边问并引用当前选项、提交后逐项解析；用 375px/768px/1280px 截图证明图片不拉伸、对话不遮挡主要操作、键盘可完成选择和提交。

**技术流程/栈与面试追问**

React compound components 渲染 `text/source/tool_status/error` message parts，SSE 驱动增量状态。追问重点是“为何不展示原始思维链”，证据是 UI 只展示真实 trace 事件与引用，同时保留可取消、可重试和开发详情。

### L. API、架构和工程可读性

#### L1. 两套 API client 和旧页面造成概念漂移

**问题**

`api.ts`、`v3Api.ts` 都有题库、练习、评测和 provider 能力；`TrainingCenter.tsx` 等旧页面存在，但当前主路由只有 `/study`、`/workbench`、`/lab`。

**改造规划**

统一为按域拆分的 client：

```text
frontend/src/api/
├─ questionBank.ts
├─ practice.ts
├─ tutor.ts
├─ memory.ts
└─ evaluation.ts
```

所有请求类型从后端 OpenAPI/Pydantic schema 生成或集中维护；旧路由和重复 fallback 删除或明确标记 deprecated。

**技术流程/栈与面试追问/证据**

按 OpenAPI 生成 TypeScript type/client，compat adapter 只保留一个版本周期；构建期检查重复 endpoint 和未使用旧 client。证据是删除旧 client 后类型检查、构建和主链烟测仍通过。

#### L2. 数据源、运行态和 artifact 没有明确边界

**改造规划**

- `content/`：版本化题库和知识库源文件。
- `runtime/`：本地运行态、SQLite、缓存，不进题库版本。
- `artifacts/`：模型评测输出，带 manifest/version/hash。
- `docs/`：用户手册、开发手册、面试证据。

后端启动时打印当前 `bank_version`、`kb_version`、`eval_version`；前端在详情页显示版本，不在主流程展示内部路径。

**技术流程/栈与面试追问/证据**

用内容寻址 hash 和 manifest foreign key 连接 source/runtime/artifact；展示任一 eval/attempt 可回查题库、知识库和代码版本，runtime reset 不删除版本化内容。

#### L3. API 设计建议

**改造规划与技术流程/栈**

```text
GET  /api/question-banks
GET  /api/domains
GET  /api/question-banks/{bank_id}/questions
POST /api/question-banks/import/validate
POST /api/question-banks/generation-jobs
GET  /api/question-banks/generation-jobs/{job_id}
GET  /api/question-banks/generation-jobs/{job_id}/events
POST /api/question-banks/{bank_id}/publish
POST /api/questions/{question_id}/feedback
GET  /api/questions/{question_id}/revisions
POST /api/practice/sessions
POST /api/practice/sessions/{id}/answers
POST /api/tutor/messages
GET  /api/tutor/runs/{run_id}/events
POST /api/tutor/runs/{run_id}/cancel
POST /api/tutor/grade-open
GET  /api/learner/profile
GET  /api/learner/review-queue
POST /api/mentor/plans
POST /api/evaluations/preview
POST /api/evaluations/runs
GET  /api/evaluations/runs/{id}
GET  /api/evaluations/runs/{id}/items
```

所有 POST 作答/记忆/评测接口带 `request_id`；写入操作幂等；错误统一返回 `code/message/retryable/request_id`。

**面试追问与证据**

- 追问：为什么 stream 建立和取消要与发送消息拆开？
- 证据：message 创建返回 run_id，SSE 可重连，cancel 幂等；OpenAPI contract test 与前端生成类型一致。

#### L4. 模块边界不清会让多 Agent 退化成一个大 orchestrator 文件

**改造规划与技术流程/栈：建议后端结构**

```text
backend/app/
├─ api/                 # HTTP/SSE，只做协议适配
├─ domains/             # domain pack registry
├─ question_bank/       # collection/note/question/version/import
├─ content_factory/     # ingest/chunk/blueprint/generate/judge/repair
├─ practice/            # session/attempt/grader/FSRS
├─ tutor/               # Tutor/Mentor use cases
├─ retrieval/           # index/hybrid/rerank/citation
├─ evaluation/          # manifest/candidate adapter/scorer/artifact
├─ agent_runtime/       # spec/run loop/tools/events/budget/checkpoint
├─ providers/           # LiteLLM/OpenAI-compatible/local adapters
└─ observability/       # OTel/Langfuse/metrics
```

Agent 不能直接操作数据库表；只调用 application service/tool contract。`content_factory` 负责 job 状态，`agent_runtime` 负责模型—工具循环，`question_bank` 负责发布和版本，避免三处都出现 `publish_question()`。

**面试追问与证据**

- 追问：Agent runtime 与业务 workflow 的边界是什么？
- 证据：runtime 不依赖 Question ORM；替换一个 fake tool registry 可独立跑测试，业务模块通过 typed tool contract 接入。

### M. 可靠性、可观测性和安全

#### M1. Agent 工具虽然有收据，但缺少业务级指标

**改造规划**

每次 run 同时记录：

- 用户任务是否完成。
- 是否调用了正确工具。
- 是否泄露答案。
- 是否正确写入一次 attempt。
- 检索是否命中题目绑定证据。
- 评分是否结构化且可解释。
- 延迟、token、重试次数和失败原因。

工具调用、模型调用、检索、评分和 memory update 使用统一 trace/span；参考 [Langfuse tracing/evaluation](https://langfuse.com/docs) 或 OpenAI Agents SDK tracing。

**技术流程/栈与面试追问/证据**

OpenTelemetry span 统一 `run_id/session_id/agent/tool/model/prompt_version`，Langfuse 记录 LLM/retrieval/eval score；展示一次 Tutor run 从用户目标到工具、引用、输出和 memory gate 的完整链。

#### M2. 失败恢复不能只做演示注入

**改造规划**

真实需要覆盖：provider timeout、429、无效 JSON、模型拒答、图片读取失败、向量库不可用、重复提交、浏览器断线。每类故障有：最大重试次数、退避、是否可 fallback、是否写入状态、用户可见提示。

成功恢复不能掩盖第一次失败；详情页显示“第一次超时，重试成功”，但不把 fallback 结果当 provider 结果。

**技术流程/栈与面试追问/证据**

按错误类型配置 tenacity/backoff、circuit breaker、checkpoint 和 idempotency；故障注入证明重试不重复 attempt/publish，candidate eval 超时不触发模型替换。

#### M3. 医疗和隐私边界

**改造规划与技术流程/栈**

- 只使用公开、合规或自制合成数据，不放患者姓名、住院号、原始医院内网地址或密钥。
- 教学题、模型评测和报告草稿都标注用途和来源。
- 不输出独立诊断和治疗方案；开放题越界时只反馈“超出当前证据范围”。
- API key 不写日志、数据库、trace、localStorage 或导出 artifact。
- 模型结果必须显示“真实调用/本地规则/格式预览”的来源状态。

密钥使用 request-scoped secret wrapper，日志/trace sanitizer 屏蔽敏感字段；source registry 与用途标签约束公开内容。

**面试追问与证据**

- 追问：如何证明 API key 没有在异常或 trace 中泄露？
- 证据：secret leakage test、脱敏异常日志、来源状态截图和医疗提示只在必要位置出现的页面。

### N. 大模型算法岗的并行改进方向

此方向是独立于刷题产品的研究入口，避免把“题库业务”与“模型能力”混在一起。

#### N1. 评测协议升级

**改造规划与技术流程/栈**

使用冻结的 `model_eval` manifest，按部位、任务和难度分层；至少保留 train/dev/test 或 calibration/test 的区分。每次实验记录模型版本、量化方式、prompt 版本、seed、显存、延迟和原始逐例结果。

**面试追问与证据**

- 追问：只有少量图像时如何避免过度结论？
- 证据：报告逐例结果、样本数/区间和 split hash，只把实验写成可复现小样本对比。

#### N2. 结构化输出和可复现推理

**改造规划**

对模型输出使用 JSON schema：

```json
{
  "organ": "stomach",
  "findings": [{"label": "...", "confidence": 0.0}],
  "evidence_region": {"x": 0, "y": 0, "w": 0, "h": 0},
  "abstain": false,
  "reason": "..."
}
```

同时报告 JSON parse rate、事实准确率、越界率和 P50/P95，不只报告一个总分。

**技术流程/栈与面试追问/证据**

Pydantic/JSON Schema 做 constrained parsing 和 repair-once；保存 raw output 与 parsed output。面试展示 schema violation 样例、修复前后 parse rate 和事实指标，不能只优化格式成功率。

#### N3. 轻量微调/对齐实验

**改造规划与技术流程/栈**

- QLoRA：只在有教学题格式或医学视觉数据时使用；对比 frozen baseline，报告可训练参数比例、显存、吞吐和事实泛化。
- SFT：针对结构化观察输出和题目讲解格式，不把合成 benchmark QA 当成临床能力提升证据。
- DPO/偏好对齐：偏好“证据充分、表达克制、结构合法”的回答；单独报告安全边界率和事实准确率，不能把安全措辞改善写成医学知识提升。
- 蒸馏：如果资源允许，将较大模型的结构化讲解/评分行为蒸馏到小模型；用 dev 校准，test 只做一次冻结比较。

Transformers + PEFT/TRL + bitsandbytes，实验配置和结果写入版本化 artifact；优先做 baseline → structured prompt → QLoRA/SFT → preference alignment 的逐步对照，不把不同变量一起更换。

**面试追问与证据**

- 追问：QLoRA/DPO 的提升来自模型还是 prompt/data leakage？
- 证据：冻结 test、相同 decoding、消融表、训练曲线、显存/吞吐和失败 run；没有完成的实验不写进简历。

#### N4. 部署和服务化

**改造规划与技术流程/栈**

统一用 vLLM/TGI/Ollama 中的一种 OpenAI-compatible 服务，记录 batch size、并发、KV cache、量化和显存。应用侧通过 ModelAdapter 调用，不把部署细节硬编码在题库服务中。

**面试追问与证据**

- 追问：吞吐和单请求延迟如何取舍？
- 证据：同一模型在不同并发/batch/量化下报告 TTFT、tokens/s、P95、显存和错误率，并由 ModelAdapter 的 model revision 固定实验条件。

### O. 测试、验收与作品集证据

#### O1. 内容和数据测试

**改造规划与技术流程/栈**

- JSON Schema/Pydantic 校验全部题目。
- 检查重复题、空选项、错误答案数量、未授权图片、缺失引用。
- 检查 teaching/eval bank 不交叉泄漏。
- 检查图像文件存在、尺寸、比例和 alt。
- 自动生成题覆盖 parser/chunk/span 定位、规则门禁、Judge 阈值、最多重写次数、语义去重和发布版本。
- 以 30—50 条小型标注集校准 Judge；至少报告通过题 precision、错误题召回和分歧样例。

**面试追问与证据**

- 追问：内容流水线最容易漏测什么？
- 证据：保留 invalid fixtures、Judge calibration report、license/source 检查结果和发布失败 artifact。

#### O2. 练习和 Agent 测试

**改造规划与技术流程/栈**

- 每种题型至少 5 个 golden cases。
- 客观题 grader 单元测试和边界测试。
- 开放题评分用人工标注小集校准，记录误判样例。
- Agent tool-call schema、答案不泄露、幂等写入、重试/超时/断线测试。
- 记忆晋升、撤销、复习间隔和 sibling burying 测试。
- Tutor pre-submit context 不含 answer key；L1/L2/L3 提示做答案泄露回归。
- Harness 覆盖 max_steps、token budget、cancel、checkpoint/resume、重复副作用防护和 Agent 工具权限。

**面试追问与证据**

- 追问：LLM 输出不确定，Agent 如何做稳定回归？
- 证据：确定性 grader/tool contract 单测 + frozen model fixtures + 少量真实 provider eval 分层运行，不用一次线上模型结果替代回归。

#### O3. RAG 和模型评测测试

**改造规划与技术流程/栈**

- BM25、dense、hybrid、hybrid+rerank 四组对照。
- Recall@K、MRR、nDCG、Context Precision/Recall、Faithfulness。
- BYOK 真实调用、无 key、错误 key、超时、429、无效 JSON 五类 provider 测试。
- 每个评测 artifact 与 manifest hash、代码 commit、prompt version 绑定。

**面试追问与证据**

- 追问：RAG 评测与候选模型评测如何避免数据泄漏？
- 证据：teaching/retrieval/eval 三套 manifest、server-only answer key、相同 hash 才可对比的 artifact。

#### O4. 前端 QA

**改造规划与技术流程/栈**

- Playwright 覆盖：选择题、提交、查看逐项解析、错题复习、收藏、导入校验、模型评测。
- Playwright 覆盖：刷题中展开 Tutor、引用选项、流式取消、超时恢复、提交错题反馈、查看生成 job 进度。
- 桌面和 375px/768px/1280px 三个尺寸。
- 无横向滚动、无 console error、所有 icon button 有可访问名称。

使用 Playwright + axe + MSW/故障注入；视觉截图覆盖纯文本题、单图、多图、Tutor 展开、生成 job 和模型评测。

**面试追问与证据**

- 追问：如何证明不是只在自己的屏幕上好看？
- 证据：三档视口截图、键盘路径、无障碍报告、网络超时/断线恢复录像和 CI smoke 结果。

## 5. 版本化实施顺序（后续修改按此执行）

| 阶段 | 目标 | 主要产物 | 不能跳过的验收 |
|---|---|---|---|
| P0 Scope Lock | 确认题库、题型、Agent、评测边界 | 本文 + API/data schema | 用户确认 Keep/Cut/Defer |
| P1 通用题库内核 | Domain/Collection/Note/Card、taxonomy、模态与导入校验 | 内镜 domain pack、JSONL/CSV/Markdown schema、source registry | 纯文本/图文题并列可刷；新增 domain/题目不改练习引擎；公开内容有 license/version/hash |
| P2 练习引擎 | 会话、多题型 grader、错题/收藏/FSRS | 练习页、结果页、attempt/review API | 单选、多选、判断、简答端到端可刷；同 note sibling 可调度 |
| P3 实时 Tutor | 边刷边问、分级提示、逐项讲解、流式 UI | 自研 run loop、typed tools、SSE、Tutor Sidecar | 不同意图走不同工具；提交前无答案泄露；P95 延迟可量化 |
| P4 RAG + Mentor | 题库 KB、hybrid+rerank、长期画像和计划 | Qdrant、检索报告、复习队列、Mentor plan | BM25/dense/hybrid/rerank 对照；建议能引用 attempt/mastery |
| P5 自动题库工厂 | 文档生成、Judge、去重、版本、用户纠错 | generation job、QuestionDraft/QualityDecision、Repair queue | 文档页码可追溯；失败定向重写；反馈产生新 revision 并回归 |
| P6 BYOK Eval | 用户模型真实评测 | 评测集选择、一次性 key、逐题结果、artifact | 明确显示真实调用；候选失败不换模型；答案不泄露 |
| P7 多 Agent 与恢复 | Generator/Judge/Repair/Evaluation 职责、checkpoint | AgentSpec、权限、event log、checkpoint/resume | 中断后不重复发布/写 attempt；不同 Agent 工具权限测试通过 |
| P8 产品化收口 | 人话 UI、图片、响应式、文档 | 用户手册、三分钟演示、面试证据 | Playwright smoke、无开发术语首屏、三尺寸无布局问题 |

## 7. 最终验收标准（完成 v2.2 才能进入简历更新）

只有同时满足以下条件，才把项目重新写成“内镜医师刷题 Agent”：

- 用户打开首页能看到多个部位题库、题型和真实题量，而不是 5 个病例卡片。
- 纯文本知识题、材料题和图文题都是正式题库能力；图片字段可选，只有需要视觉推理的请求才调用 VLM。
- 用户可以完成单选、多选、判断、简答，并在提交后看到逐项解析和下一步复习动作。
- 用户在提交前可以引用当前题/选项/图像区域向 Tutor 追问；Agent 至少根据“提示/术语/知识追问/提交/讲解/复习/建卡”选择不同工具路径。
- Tutor 的答案 key 上下文隔离、TTFT/完整延迟、取消/超时和来源引用都有可复现测试。
- 开放题评分有题目绑定的 Rubric、知识库证据和结构化评分理由。
- 题库 RAG 有可复现的 chunk、metadata、dense+sparse、rerank 和检索指标。
- 记忆区分当前会话、作答事件、长期画像和复习卡，且能撤销错误更新。
- 用户上传一个带章节的文档后，可以看到解析进度、知识单元、生成多题型、Judge 分项、定向重写、去重和自动发布；任一题可定位原文。
- 用户能标记错误题；Repair 生成新 revision、重新经过规则/Judge/回归，旧 revision 不再进入新练习。
- Tutor、Mentor、Generator、Judge/Repair、Evaluation 的 prompt/tool/context/memory/output 各不相同；普通索引服务不被包装成 Agent。
- 自研 Harness 可以展示 typed tool、budget、timeout、cancel、checkpoint/resume、幂等副作用和 trace，框架使用边界能用代码说明。
- 模型评测页允许选择冻结评测集并真实调用一次性 API；没有调用就不显示模型得分。
- 首屏使用研修医能理解的人话；工程术语只在高级详情出现。
- 所有公开数据有来源和 license；所有医疗输出保留教学/医生复核边界。
- 增加一个最小通用 domain pack 后，无需修改练习/FSRS/Tutor/评测核心即可运行。
- 测试、artifact、版本号和文档能让另一个人按 README 在本地复现。

在这些条件完成前，不应继续扩写简历里的“Agent 运行时”“多步证据链”“模型评测”描述；否则面试官一追问题库、评分、RAG、API 真实性和记忆实现，就会暴露产品主线尚未闭环。
