# TiBan V3.5.2：多模态 RAG 简历与面试准备

本文记录当前代码真实实现的技术关键词、评测口径和面试回答。文中的
Recall、准确率与时延必须以本机实际运行 `benchmark_multimodal_rag.py`
输出为准；不能把文本 RAG 的结果直接写成图片检索结果，也不能把工程样本
结果描述成临床有效性。

## 简历表述建议

### 一句话版本

实现图文可追溯的多模态 RAG 学习链路：用 PyMuPDF 完成版面感知解析和
Figure-caption 对齐，使用 BGE-M3 与 CLIP 进行文字/图片检索，结合 Qdrant
payload 过滤和受控概念图完成一跳跨模态证据扩展，并将图片、图注、页码和
来源作为真实视觉上下文交给 Tutor/Mentor。

### 项目经历版本

- 构建面向消化道内镜教学资料的 Multimodal RAG：在 PDF 解析阶段读取文本块、
  图片位置和 Figure caption，将图片与页码、章节、图注及对应文本片段建立
  可追溯关联；对 Logo、页眉和无图注装饰图进行过滤。
- 设计 BGE-M3 文字混合召回、CLIP 文本到图片召回和受控 Evidence Graph
  一跳扩展的三路检索链路；Qdrant payload index、批量 upsert、候选集约束、
  进程内短 TTL 缓存降低重复查询开销，所有结果保留可解释的来源关联。
- 打通视觉 Agent 上下文：图像题或用户粘贴/拖入图片时，沿统一的
  OpenAI-compatible Provider 调用链组装文本内容块与 image content block；
  不支持视觉输入时返回明确错误，不把图片地址写进文字后伪装成模型已读图。
- 以 Recall@3、图注/页码正确率、文字到图片/图片到文字关联率、图谱噪声率、
  P50/P95 检索时延和热查询吞吐评估链路质量，评测样本仅使用已登记并获许可
  的内镜教学资料 Figure caption，不混入 EndoBench 学习题库。

## 多模态 RAG 的质量如何判断

质量不是只看 Agent 最终回答是否“像正确答案”，而是拆成检索、证据关联和
生成三层。当前仓库已落地前两层的可执行评测，生成层可在接入视觉模型后用
相同证据包做人工或模型辅助评审。

| 层次 | 指标 | 计算口径 | 当前用途 |
| --- | --- | --- | --- |
| 检索命中 | Image Recall@3 | 预期 Figure 是否出现在前三个图片结果中 | 衡量图片召回是否漏掉目标 |
| 证据定位 | Caption/Page Accuracy | 命中的图片图注和页码是否同时正确 | 衡量 provenance 是否可追溯 |
| 双向关联 | Text→Image / Image→Text | 文字证据能否找到 Figure，图片能否回到绑定文本 chunk | 衡量跨模态证据链是否闭合 |
| 图谱治理 | Graph Noise-free Rate | 返回关系中不出现 logo、页眉、article 等无意义节点 | 衡量图谱是否被版面噪声污染 |
| 生成可信 | Faithfulness | 回答中的可核查陈述是否被召回证据支持 | 需在视觉模型链路上做回答级评审 |
| 生成覆盖 | Answer / Context Recall | 参考答案需要的证据是否被召回并用于回答 | 区分“找到了”与“答完整” |
| 性能 | P50/P95、QPS | 记录典型时延和尾延迟；QPS 为单位时间完成的查询数 | 衡量交互体验与并发能力 |

本地运行：

```powershell
cd code/backend
$env:PYTHONPATH='.'
python scripts/benchmark_multimodal_rag.py --strict
```

脚本只读当前数据库、Qdrant 和评测样本，不复制原始 PDF，不写入图片、API
Key 或运行时评测产物。它将首次图文查询与同查询的稳定热路径分开计时；热查询
吞吐是单进程顺序测量，不等同于并发压测。四条 Figure caption 样本适合做链路
回归，不足以支持医学效果或大规模线上效果结论。若需要更有统计效力的指标，
应增加经过授权的人工标注查询，并固定 train/dev/test 划分。

### 本机实测记录

2026-09-12 在本机 SQLite + Qdrant（CLIP `clip-ViT-B-32`、4 个 Figure
caption 查询）运行 `python scripts/benchmark_multimodal_rag.py --strict`，
五项证据质量指标均为 `1.000`：Image Recall@3、图注/页码准确率、文字到图片
关联率、图片到文字关联率和图谱无噪声率均通过。性能数字应按冷/热路径解释：

| 路径 | P50 | P95 | 说明 |
| --- | ---: | ---: | --- |
| 文字检索冷查询 | 455.37 ms | 643.48 ms | 包含首轮文字检索开销 |
| 文字检索热查询 | 52.97 ms | 90.98 ms | 命中有界短 TTL 检索缓存的稳定路径 |
| 图文证据冷查询 | 693.72 ms | 11363.84 ms | 包含本地视觉模型首次加载，不能当作稳定交互时延 |
| 图文证据热查询 | 193.62 ms | 296.69 ms | 稳定路径；顺序热查询吞吐为 4.67 QPS |

因此，简历中可以写“建立了可追溯的多模态 RAG 评测闭环，并区分冷启动与热路径
时延”；如果需要写数字，应注明“本机、4 条 Figure caption 回归样本、CLIP
热路径 P50 193.62 ms”，不要把冷启动 P95 包装成线上性能，也不要把四条样本的
`1.000` 写成临床准确率。

## 关键技术问答

### 1. 你的多模态 RAG 和普通文本 RAG 的区别是什么？

普通文本 RAG 只在文字 chunk 上召回；TiBan 额外把资料中的有效图片与
Figure caption、页码、章节和文字 chunk 绑定，再用 CLIP 在文字/图片共享空间
中召回图片，最后通过受控概念图补齐文字到图片、图片到文字的证据路径。返回给
Agent 的不是裸图片，而是带来源、图注和页码的证据包。

### 2. 图片是怎么和 Figure caption 对齐的？

PDF 解析时读取图片的版面矩形和文本块矩形，在同页候选中按相对位置选择最近的
Figure caption；同时要求图片通过 MIME、文件头、尺寸和像素检查，并过滤没有
图注的低信息图片。资产的页码、图注和哈希存入受控媒体表，图片向量 payload
只保留不透明资产 ID 和紧凑 provenance。

### 3. 为什么需要 CLIP 和 BGE-M3 两套模型？

BGE-M3 更适合文字语义检索，负责段落和图注上下文；CLIP 让文字查询可以进入
图片向量空间，负责找视觉证据。两者不是简单拼接分数：系统保留各自的召回通道，
只对同页、同图注或受控概念匹配添加有限的证据关联信号，避免把一个不可解释的
分数包装成置信度。

### 4. 你如何证明图片检索不是“看起来能搜”？

使用固定 Figure caption 查询和预期页码，计算 Image Recall@3、图注/页码正确率、
双向关联率，并检查图谱噪声节点。还要记录冷查询和热查询 P50/P95，分别观察
首轮模型/索引开销与缓存后的交互时延。若目标图没召回，即使 Agent 最终猜对，
也不能把该样本算作检索成功。

### 5. Recall@K、Precision 和 Faithfulness 分别看什么？

Recall@K 看预期证据是否出现在前 K 条，漏召回会直接拉低它；Precision 看前 K
条中有多少是真正相关证据；Faithfulness 看回答陈述能否被召回上下文支持。
前两个主要评估检索，后一个评估生成是否忠于证据，三者不能互相替代。

### 6. 你的 GraphRAG 是复杂多跳推理吗？

当前准确表述是“基于 Figure caption 和受控概念图的一跳跨模态证据扩展”。
文本 chunk 中的受控概念与 Figure 节点建立 `depicted_in_figure` 关系，查询命中
文本后可找到图片，图片也能回到绑定文本。关系始终带有来源 chunk，不使用页眉、
OCR 残词或无约束实体生成，暂不把它包装成复杂多跳自主推理。

### 7. 如何降低多模态 RAG 的时延和提升吞吐？

先限制候选池，再做重排；使用 Qdrant payload index 加速 document/domain/
namespace/version 过滤；索引阶段批量 embedding 和 upsert；对不含敏感信息的
检索投影使用有界短 TTL 进程缓存，并在资料启停、重建、删除后清空缓存。评估时
同时报告 P50、P95 和热查询 QPS，不能只报平均值；图片字节不进入缓存。

### 8. Tutor 如何真正看到当前题目的图片？

Practice 后端从受控题目图片资产解析路径，沿 Tutor 的真实 Provider 调用链加入
文本内容块和图片内容块；支持视觉的 OpenAI-compatible 模型收到实际图片输入。
如果 Provider 或模型不支持视觉能力，发送前或响应阶段返回明确的能力错误，系统
不会只保留图片 URL 并继续声称模型已完成图像分析。

### 9. 题库图片为什么不进入知识库图片向量检索？

学习题库图片和知识资料图片的业务语义、权限和生命周期不同。题库图片只服务于
刷题、审核和 Tutor 当前题目上下文；知识库图片索引只接收已登记的学习资料，
这样可以避免一道题的图片污染资料召回，也避免题库内容被当成外部知识证据。

### 10. 多模态知识库如何处理数据治理和隐私？

图片采用受控资产目录，数据库和向量 payload 只存资产 ID、哈希、MIME、尺寸和
来源元数据；响应不会携带 Base64，日志和任务消息不记录图片字节或 API Key。
资料必须经过来源与许可检查；医学输出仍属于教学研修或医生复核前辅助，不作为
独立诊断依据。

### 11. 目前哪些数字可以放进简历？

先区分数字来源：文本 RAG 的 Recall@5 只能标为文本检索基准；多模态数字必须
来自 `benchmark_multimodal_rag.py` 的图片评测；P50/P95 必须注明本机配置和样本
规模。四条 Figure caption 只能说明链路回归通过，不能写成临床准确率或线上规模
吞吐。面试时主动说明数据边界，反而能证明评测口径清楚。

## 当前限制与后续扩展

- 当前示例评测集是小规模、来源受控的 Figure caption 回归集；需要更多授权资料
  和人工标注后，才能做更稳健的跨文档统计。
- GraphRAG 当前是证据绑定的一跳扩展，不包含复杂多跳规划或模型自建知识图谱。
- 多模态知识库暂不做图片批量人工管理和图片向量重训练；图片检索使用现有
  CLIP/FastEmbed Provider 边界。
