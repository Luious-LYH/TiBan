# v1.0 Stage 1 pre-implementation audit

**Audit date:** 2026-08-29
**Execution boundary:** `EndoTutor_4_Stage_Optimization_Roadmap.md`, Stage 1 only
**Audited baseline:** `refactor/v3-agent-learning-platform` at `e66cdcb`
**Change policy:** this document is read-only audit evidence. No product logic,
database schema, API contract, source data, secret, or existing user worktree
change was made by this audit.

## Decision

The repository is not a blank Demo and must not be rebuilt around new
architecture terminology. Stage 1 can be completed by consolidating the
canonical current product path around its existing persisted state:

```text
Practice submit
  -> immutable Attempt
  -> deterministic LearnerMastery + ReviewCard/FSRS projection
  -> next-session selection reads that state
  -> learner-visible recommendation reason
```

The missing link is the final selection/recommendation step, not a new
`LearningState` database model or a general Agent framework.

## Current canonical path

| Concern | Current source of truth | Audit finding |
|---|---|---|
| Question contract | `backend/app/schemas/stage1.py` | Four discriminated public/grading variants already exist: `single_choice`, `multiple_choice`, `true_false`, `short_answer`. Do not recreate a universal question schema. |
| Persistent learning state | `backend/app/db/models.py` | `AttemptModel`, `LearnerMasteryModel`, `ReviewCardModel`, `PracticeSessionModel`, and `PracticeSessionItemModel` already cover the Stage 1 state concept. |
| Deterministic write-back | `backend/app/db/repositories.py` + `backend/app/services/learning_service.py` | `record_attempt` stages an immutable Attempt and deterministically applies mastery and real FSRS scheduling. No LLM tool writes durable learning state. |
| Learner product routes | `frontend/src/app/router.tsx` | The current main surface is `/`, `/banks`, `/practice`, `/eval`; old portfolio pages are not imported by the main router. |
| Tutor | `backend/app/services/agent_runtime.py` | The bounded single-Agent runtime, permissioned tools, ToolReceipt and SSE already exist. No LangGraph/Multi-Agent rewrite is justified. |
| Retrieval | `backend/app/services/rag_service.py` | PostgreSQL remains citation/source authority and Qdrant remains the retrieval index. Dense/sparse/hybrid/rerank implementations already exist. |

## Observed gaps

### Adaptive loop is only half-connected

The submit path writes `Attempt -> LearnerMastery -> ReviewCard/FSRS`, but
`Stage1Repository.create_session` currently samples randomly. The current
`PracticePage` creates a server session but displays the first items from a
separate question-list response instead of consuming the server session's
persisted membership/order. Therefore the main learner flow does not yet prove
that a later session changes because of a learner's prior state.

Stage 1 should change only this canonical selection path. It should prioritise,
within the selected learner-ready bank, due reviews first, then weak topic
coverage, then unseen/coverage questions. A concise reason can be derived at
selection time from the existing records and returned on the existing session
response; it does not require a new persistence schema.

### Existing legacy recommendation code is not a shortcut

Legacy portfolio services contain separate recommendation structures, but they
are not part of the current main router. Reconnecting or copying those models
would create parallel state and violate the Stage 1 consolidation goal. The
canonical SQLAlchemy state above is the only allowed foundation for the
adaptive-loop work.

### Tutor story needs small clarification, not a runtime rewrite

The current Tutor can read public question context, retrieve knowledge, read a
learning overview, and read grading results only after submit. It already has
no durable write tools. Stage 1 may add a read-only `get_recent_mistakes`
observation backed by existing Attempt/Mastery records, document the existing
`messages/current_question/current_attempt/learning_context/last_observation/step`
state, and extend regression evidence. It must not add general orchestration
or a second Agent.

### Retrieval decision is not aligned with its existing evidence

`docs/evals/rag-benchmark-v2.md` reports held-out Recall@5 of 0.8833 for Dense,
0.7167 for Hybrid RRF, and 0.9000 for Hybrid + rerank at materially higher
latency. The Tutor currently calls the Hybrid path. Before changing the product
default, Stage 1 must tune only the development split, rerun the frozen
held-out split once, then document the selected effect/latency trade-off.

## Explicit non-goals

- No whole-repository Hexagonal/Ports/Adapters rewrite.
- No Python-to-TypeScript backend migration.
- No Multi-Agent, RL, autonomous self-modification, prompt evolution, or new
  learning domain.
- No new data ingestion, real patient data, secret persistence, or change to
  the EndoBench evaluation-only boundary.
- No reviving old page copies or duplicated legacy state as the main product
  path.

## Implementation guardrails

1. Keep `QuestionPublic` answer-free and preserve the existing typed
   discriminated union.
2. Keep `grade -> Attempt -> mastery -> review schedule` deterministic and
   server-owned.
3. Only the existing current routes may consume new adaptive-session behavior.
4. Run OpenAPI generation after any public response change; do not hand-edit
   generated response types.
5. Preserve pre-existing uncommitted user artifacts and historical documents;
   do not reset, clean, or fold them into a Stage 1 commit.
6. Treat all existing RAG/Judge figures as engineering evidence, never clinical
   effectiveness evidence.

## Scope-lock result

The requested Stage 1 is small enough to proceed without a platform rewrite
after scope confirmation. It consists of: adaptive session selection plus
reason, a small Tutor state/evidence clarification, retrieval-default evidence,
Tutor quality evaluation, release-proof checks, and v1.0 portfolio packaging.
Stages 2 through 4 remain out of scope.
